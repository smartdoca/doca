# 统一存储实现

状态：2026-10-03。用户确认只支持新版本，不兼容旧版。新增宿主数据库基线为 `doca-2026-10-03-storage-v1`，安装清单为 version 2，SDK 源码为 0.1.7。版本号不代表已经发布 npm 或部署到生产。

## 存储与插件边界

宿主通过环境变量选择数据存储和文件存储。数据库继续使用 `DOCA_DATABASE` / `DOCA_DATABASE_URL`；SQLite 用于单实例，水平部署使用共享 PostgreSQL。文件存储必须设置 `DOCA_FILE_STORE_ID`、`DOCA_FILE_STORES_JSON`，不读取数据库中的后端配置或凭据。例如：

```dotenv
DOCA_FILE_STORE_ID=local
DOCA_FILE_STORES_JSON='{"version":1,"stores":{"local":{"provider":"local","root":"/data/storage"}}}'
```

S3 配置项为 `provider:"s3"`、`bucket`、`region`、`forcePathStyle`、`credentials:{accessKeyId,secretAccessKey,sessionToken?}`，可选 HTTPS `endpoint` 与 `cdn:{domain,keyPairId,privateKey}`。配置严格校验，诊断不包含输入及密钥。多实例协作还需要共享 `DOCA_REDIS_URL`。每个实例使用相同配置；本地后端必须挂载同一个共享持久化目录。存储 ID 与物理位置在写入数据后须保持不变；改位置不等于迁移数据。引用未配置 ID 时明确失败。

数据库的 `storage_profiles` 只记录稳定存储 ID、启用状态和建立时间；所有对象继续通过稳定 ID 引用。管理界面只读展示配置，PUT 返回 405。身份、消息网关和搜索凭据不属于本次抽离；`service-credentials` 不再含 storage 字段。

插件通过 `@smartdoca/plugin-sdk/storage` 注入 `pluginDatabaseToken`（`storage.sql.v1`）和 `pluginObjectStorageToken`（`storage.objects.v1`）。句柄在安装时绑定插件 ID、dataVersion 和安装代次，插件不能选库、提交原始 SQL、指定存储 key 或读取宿主连接配置。逻辑库是 `plugin:<pluginId>`；物理业务表使用 `plugin_` 前缀及 ID、代次、表名的确定性 SHA256 映射，以避免 PostgreSQL 名称长度限制和点/连字符归一化冲突。SQLite 与 PostgreSQL 都使用宿主连接和命名空间业务表，隔离由结构化 SDK 查询强制落实。

常规文件使用 `files.v1` 的文件夹系统和现有用户权限，不改稳定文件/文件夹 ID。宿主创建的数据归属为 `host`，插件新建的归属为 `plugins/<pluginId>`；原始和派生对象遵守同一前缀。去重限制在同一命名空间，引用其他用户文件不改变其归属或授权。内容、模板、素材继续通过已有通用注册、发现和授权读取方法访问。

特殊私有对象位于 `plugins/<pluginId>/objects/<generation>/<objectId>/<attemptId>`。SDK 返回不透明 ID 和元数据，单对象最多 32 MiB。上传完整、读回校验后才提交数据库引用。读取核对大小和 SHA256。删除先使数据库引用失效，持久化垃圾清理意图，随后回收字节；失败的回收由宿主启动及定时任务重试。不承诺正在进行的读取在并发删除后继续成功。上传成功而数据库提交失败可能留下无引用对象；本实现不自动扫描或删除这类对象。

插件仍在受信任 Node.js 进程中运行；SDK 作用域不是进程或操作系统沙箱。凭据托管和临时工作区仍未导出，本次不把拟议接口写成已经实现。

## 安装与启动

1. 宿主静态检查完整包、SDK 范围、依赖、版本、dataVersion 和远端元数据；外部包必须声明 `doca.storage:"host"`，SDK 范围最低版本至少 0.1.7。安装阶段不执行插件工厂。
2. 将完整不可变 ZIP 写到 `host/plugin-releases/<sha256>.zip`。本地使用临时完整文件及原子 link；S3 使用条件写入，完整读回检查 SHA256 和大小。
3. 数据库事务以修订号 CAS 提交归档引用、逐文件哈希索引、目标清单和插件存储身份。数据库不保存 ZIP 字节。失败不产生指向不完整包的清单；无引用归档保留。
4. 运维逐个重启全部实例。响应实例的清单只报告该实例的运行版本，并核对其启动时的安装代次；同版本卸载重装也会提示旧实例待重启。不代表集群所有实例已完成重启；没有自动重启或版本协调器。
5. 实例检查本地完整文件集和逐文件哈希。命中时不重新下载 ZIP；缺失、额外文件、符号链接或损坏时，从统一存储读回并校验，使用临时目录重建代码缓存。恢复不访问插件商店、不执行 npm install 或构建脚本。
6. 静态声明与清单完全一致后才导入代码，检查运行时声明和必需的 uninstall 钩子并初始化。失败拒绝启动。Web 静态资源按不可变版本恢复，支持不同实例的资源请求。

业务库由插件显式声明完整 version 1 结构，包括 text/integer/real 列、是否可空、主键和唯一约束。首次建库和声明在同一事务中提交，重复声明必须完全一致；缺表或结构不同明确拒绝。整数为 32 位，real 使用双精度。查询只访问声明的表/列；更新和删除必须有过滤条件。事务回调只执行一次，不自动重试；回调退出后句柄失效。

停用和 dispose 保留数据。卸载成功时，注册清单、命名空间失效、私有业务表删除和私有对象清理意图在同一数据库事务提交。旧实例句柄被代次检查拒绝继续写入；重新安装创建新代次。用户文件、权限、上传回执和历史发行包保留。仅同一有效安装代次的升级/启停可取消待应用变更；初次安装、已卸载或不同代次不通过取消恢复数据，须显式卸载或重启。业务 uninstall 钩子的外部副作用不属于数据库事务；仍需运维统一重启，不承诺任意外部副作用自动回滚或集群业务任务排空。

## 旧数据处理

旧宿主基线、registry version 1、数据库 ZIP 内容、旧存储配置形状和 SDK 范围均明确拒绝。删除原来给已有基线自动补建插件表的入口。已有库不会迁移、补缺省字段、双读写、转换、清空或重建；保留原数据，需要新空数据库部署新版。

没有迁移命令或配置导出工具。原自管业务数据库和目录不读取、不导入、不删除；不能把新空库称为已接续旧业务数据。回退通过原部署、原数据库和原存储进行，新部署数据单独保留。

## 验证

仅使用临时目录和隔离数据库。覆盖命名空间隔离、事务回滚、过期句柄、同代次多连接、旧格式拒绝、缓存修复/免下载、归档不可变提交、PostgreSQL 修订号并发冲突、S3 条件写入和字节完整性。SDK 通过独立构建产物消费者验证。浏览器覆盖与外部依赖限制记录在验收报告中。

安装执行记录的 active 表示共享审计中尚未记录终态，不代表响应实例拥有该请求，也不能证明进程仍存活。进程崩溃后的未决记录不会被伪装为成功。
