# 大数据量列表审计

本文记录 Doca 中可能随用户、文档或事件数量持续增长的列表，以及它们在深分页、精确计数、前端累积和固定上限方面的风险。第一版优先处理资源与最近访问主链路；其余模块按风险分批迁移。

## 第一版已处理

| 模块 | 原问题 | 第一版处理 |
| --- | --- | --- |
| 最近访问与通用资源查询 | `resource_visits` 相关子查询、每页精确计数、深 offset | 访问记录改为索引关联；增加稳定排序复合索引；最近访问不做精确总数；游标页不重复计数；所有者权限走快速路径 |
| Web 工作台 | offset 加载、所有已加载行直接参与布局、无时间分组 | 使用服务端游标；按今天、昨天、最近 7 天、最近 30 天和更早分组；对屏外行启用浏览器内容跳过 |
| Web 全局搜索 | 数据库结果继续使用 offset | 数据库返回游标时优先使用游标；搜索引擎的有界排名结果保留 offset |
| 移动端资源列表 | `FlashList` 只加载第一页 | 改为 React Query 无限查询，通过 `onEndReached` 继续读取游标页 |
| 资源批量消费者 | 知识库选择器、移动目标、回收站准备等循环深 offset | 改为逐页游标遍历 |
| 应用壳旧资源列表 | 已无界面消费者，但仍在知识库页面触发重复请求 | 删除旧状态、请求和未使用组件 |
| 访问写入查询 | 查询某用户某文档的最后一条事件缺少完整索引 | 增加 `(user_id, resource_id, created_at)` 索引 |

## 后续仍需治理

| 风险 | 模块与位置 | 当前形态 | 建议 |
| --- | --- | --- | --- |
| 高 | 文档树 `features/documents/tree.tsx`、资源查询 tree mode | 超限已显式提示，但仍一次读取和渲染最多 10,000 项 | 改为按层级或物化路径读取，并按展开状态加载子级 |
| 高 | 管理员成员、在线成员、目录设置 | 管理员用户和目录设置已使用游标；在线成员仍为 offset，且界面追加导致长 DOM | 在线成员迁移游标；成员表使用窗口化渲染 |
| 高 | `visit_events` | 每用户每文档每天一条，但无保留周期、无数据库日级唯一约束 | 增加 `visit_day` 和唯一键；配置明细保留期，长期统计转聚合表 |
| 中 | 通知、工单、快捷笔记、注册审核 | 30～100 条 offset 分页 | 统一迁移游标响应，避免各模块维护不同分页协议 |
| 中 | 公共发现与社区列表 | offset 分页，部分查询计算精确总数 | 使用游标；总数改为首屏可选或近似值 |
| 中 | 文档互动与历史保留 | 读取已使用游标，但访问、审计、评论与版本仍会无限增长 | 分别配置保留、归档与聚合策略；不可将删除策略与分页优化混为一体 |
| 中 | 知识库、来源和移动目标选择器 | 已改游标，但最终仍把全部结果保存在内存 | 改为可搜索的远程选择器，不再预载整个工作区 |
| 中 | Web 工作台 | `content-visibility` 降低绘制成本，但 DOM 数量仍随点击“加载更多”增长 | 后续引入真正的窗口化列表，并保留当前时间分组 |
| 低 | AI/搜索服务中的固定候选上限 | 多处有 80～1,000 条显式上限，通常用于控制模型或远端搜索成本 | 保持有界，但响应需明确说明截断，避免把上限结果误认为全集 |

## 统一分页约定

新增或迁移的可增长列表采用以下约定：

1. 排序必须有稳定的唯一尾键，例如 `visited_at DESC, resource_id ASC`。
2. 响应只返回 `nextCursor`，不同时维护 offset 分页协议。
3. 游标绑定当前用户和全部筛选条件，不能跨用户或跨筛选复用。
4. 首屏可以按产品需要返回精确总数；后续页不重复计算。最近访问等找回型视图可以完全不返回总数。
5. 前端保留加载、错误、空态和已有内容上的非阻塞刷新状态。
6. 需要遍历全集的后台任务也使用游标，但面向用户的选择器不应以“拉完全集”为交互模型。

## 验收基线

- SQLite 和 PostgreSQL 都覆盖第一页、连续游标、相同时间戳、权限过滤和游标越权测试。
- 10,000 条本人最近访问的本地 SQLite 基准，第一页和第二页应保持在同一数量级，且不随页码线性变慢。
- Web 连续加载时不得重复或漏项；跨页的时间分组只能出现一个连续分组标题。
- 移动端滚动到底部自动加载下一页，刷新后回到新的第一页，并保留明确的加载、错误和空状态。
