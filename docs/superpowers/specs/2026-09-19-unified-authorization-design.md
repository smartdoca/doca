# 统一授权来源与权限计算方案

记录日期：2026-09-19  
状态：已实现（2026-09-19）

## 1. 背景与目标

当前权限事实分散在 `grants`、`share_members` 和 `member_exclusions` 中：主动授权、链接授权和继承阻断分别由不同表及不同代码路径维护，导致用户权限调整、分享链接撤销、父子文档继承之间容易产生覆盖不一致。

目标是让一个文档用户的所有本地授权来源都进入同一张授权记录表，再由统一计算器得到有效权限。分享链接本身仍然保留独立的链接配置表；撤销记录是审计信息，不作为新的权限来源，也不阻止用户通过新链接重新获得权限。

本方案只改变命名用户授权的存储和计算方式，不改变所有者、公开权限、权限申请和资源设置继承的独立语义。

## 2. 授权记录模型

目标表可命名为 `permission_records`（也可以在迁移阶段演进现有 `grants`），一行表示一个文档用户的一种授权来源：

| 字段 | 说明 |
| --- | --- |
| `id` | 授权记录 ID |
| `resource_id` | 当前文档或知识库 ID |
| `user_id` | 被授权用户 ID |
| `source_type` | `direct`、`link`、`parent_override` |
| `source_id` | 链接分享 ID；主动授权为空 |
| `source_resource_id` | 父文档来源 ID；普通主动授权为空 |
| `role` | `reader`、`commenter`、`editor`、`manager` |
| `include_descendants` | 是否向知识库子文档传播 |
| `status` | `active` 或 `disabled` |
| `created_by`、`created_at`、`updated_at` | 来源和审计信息 |

来源数量约束：

- 同一文档、用户最多一条 `direct` 记录。
- 同一文档、用户最多一条 `parent_override` 记录。
- `link` 按 `source_id` 区分，同一链接同一用户最多一条；不同链接可以有多条。
- `disabled` 记录不能产生权限，但必须参与继承阻断判断。

`share_links` 继续保存 token、角色、有效期、人数上限、启停状态和 generation/share ID。它是链接定义，不是用户授权表。`share_members` 在迁移完成后不再作为权限事实表。

## 3. 权限计算

### 3.1 权限范围

角色等级为：

```text
reader < commenter < editor < manager < owner
```

`role` 和 `include_descendants` 是两个维度，不能把所有字段分别取最大值后拼成一个从未被任何来源授予的权限。例如“编辑但不包含子文档”和“阅读且包含子文档”不能直接合成为“编辑且包含子文档”。

计算某个具体文档的权限时，按目标文档逐层计算：

1. 当前文档的 `direct` 和 `link` 活跃记录可以贡献当前文档权限。
2. 当前文档或祖先文档的记录只有在 `include_descendants=1` 时，才可以贡献后代权限。
3. 同一目标文档上所有可用来源取最高角色。
4. 所有者和公开权限仍按原规则单独计算，最后与命名用户权限取最高值。

### 3.2 父文档继承与覆盖

普通父文档权限继续动态计算，不为每个继承用户复制静态授权记录。`parent_override` 是当前文档上的控制记录：

- `active`：使用该记录中的角色和范围替代父文档继承结果。
- `disabled`：阻断该用户从父文档继续继承，但不授予权限。
- 无 `parent_override`：正常沿父文档或知识库链向上计算。

这样既支持“覆盖父文档权限”，又不会因为父文档后续调整而留下大量过期快照。权限来源详情页可以展示一个虚拟的“父文档继承”来源；只有覆盖或阻断才落库。

个人文档没有父文档和知识库归属，因此不计算父级来源，也不允许 `include_descendants`。

### 3.3 主动授权调整

- 新增主动授权：没有 `direct` 记录就新增；已有记录则与目标权限比较并更新为目标权限。
- 如果当前只有 `link` 来源而没有 `direct` 来源，新增主动授权时必须新增一条 `direct` 记录，不能改写链接来源；已有 `direct` 记录时，再与目标角色和子文档范围比较并更新该记录。
- 用户权限页展示当前文档权限和父文档继承后的计算结果，而不是只展示某一条记录。
- 调整用户权限时，统一更新该用户在当前文档上的本地授权记录。不能修改公共 `share_links` 的角色、人数和有效期；链接来源记录只改变该用户的授权快照。
- 如果目标权限需要覆盖父文档，创建或更新 `parent_override`。
- 删除主动授权时删除 `direct` 记录；如果用户原本可以从父文档继承，则保留或创建 `disabled parent_override`，避免删除后自动回退到父权限。
- 用户之后重新获得主动授权时，不自动删除该禁用记录，也不叠加父权限；只有用户在来源详情中明确取消“阻断父权限”才恢复继承。

## 4. 分享链接兑换

兑换必须在一个事务中完成以下检查：

1. 校验 token、链接启用状态、资源状态和过期时间。
2. 查询当前文档、用户、`source_type=link`、`source_id=当前分享 ID` 的授权记录。已有记录时直接进入文档，不重复消耗名额。
3. 计算用户当前有效权限，并同时比较文档角色和子文档范围。
4. 如果用户已有权限完全覆盖当前链接：返回“已有权限”的确认结果。选择直接进入时不消耗链接；选择消耗链接时才新增一条 link 来源记录。
5. 如果用户权限低于链接权限，新增 link 来源记录。
6. 对同一分享 ID 统计活跃 link 来源记录的去重用户数；达到 `max_members` 时返回“当前链接已用尽”。插入和计数必须在同一事务中防止并发超额。

链接撤销后，该链接本身不可用；撤销不建立永久用户黑名单，因此被撤销用户可以通过新的分享 ID 再次获得权限。

## 5. 分享撤销与撤销记录

每次撤销只产生一条 `share_link_revocations` 记录：

```text
resource_id
share_id
revoked_by
revoked_at
revoked_user_ids   JSON 数组，保存本次被撤销的用户 ID
```

撤销事务：

1. 找到指定分享 ID 的全部 link 授权记录。
2. 将用户 ID 汇总写入一条撤销记录。
3. 按 `resource_id + share_id` 删除授权表中的 link 记录。
4. 将分享链接标记为 revoked/disabled。

撤销记录只用于“撤销记录”Tab 和审计查询，不参与有效权限计算。用户通过其他主动授权、父文档继承或新的分享链接获得的权限不受旧链接撤销记录影响。

## 6. 权限管理页面

用户列表按 `user_id` 聚合授权记录，展示该用户计算后的最大有效权限。每个用户提供信息入口，切换到该用户的全部来源卡片：

- 主动授权
- 各个分享链接授权
- 父文档继承或父权限覆盖
- 被禁用的父权限阻断记录

来源详情可以单独调整或删除某条记录；“取消覆盖父权限”删除或解除对应的 `parent_override`，从而恢复正常父文档继承。修改用户有效权限时不改变分享链接公共配置。

将用户权限统一调整为目标权限时，更新该用户当前文档下的全部活跃授权来源记录；只改变该用户的授权快照，不改变公共分享链接的角色、人数上限或有效期。

## 7. 当前基线

统一授权表、来源、状态和分享 ID 直接属于全新数据库基线。SQL 权限查询、内存权限计算、权限管理、分享兑换、邀请审批和权限列表只使用这一套结构。授权变化、撤销记录、通知和审计使用版本条件与事务同时提交。

## 8. 验收场景

- 同一用户拥有主动授权、多个链接授权和父级继承时，结果按目标文档正确取最大有效权限。
- 角色等级和包含子文档范围出现交叉时，不产生未被任何来源授予的组合权限。
- 同一链接重复兑换不重复占用人数；不同链接分别计算人数。
- 链接达到人数上限后显示当前链接已用尽，新链接仍可使用。
- 撤销链接后旧链接不可用，用户可以通过新链接重新获得权限。
- 删除主动授权后不会回退到父权限；重新授权不会自动叠加被阻断的父权限。
- 取消父权限覆盖后恢复父级继承；父文档权限变化可以被实时计算反映。
- 知识库父文档、子文档、个人文档分别符合继承和不继承规则。
- 权限详情可以查看、调整、删除单个来源，且不会修改公共分享链接配置。
