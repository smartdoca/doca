# 数据库升级规范

[English](database-schema-evolution.md)

已批准的用户组增量沿用本规范及当前兼容代际：七张组/成员/邀请/授权空表，及独立组搜索策略表，首次安装明确初始化为仅所在组（`system/member/revision=1`），用户覆盖为空。历史个人/链接授权、邀请、公开设置及用户目录策略不变，不转换、不复制组成员为个人授权。已安装配置行丢失不静默重建。所有服务实例与 Web 同步更新，降级保全及恢复另行评审。见[组权限规则](user-groups.zh-CN.md)、[发行说明](releases/0.2.28.zh-CN.md)及 [SQLite/PostgreSQL 17/18 验证](verification/user-groups-2026-10-30.md)。

这是 Doca 后续核心数据库改动统一遵守的开发、评审与发布规范，适用于表、字段、索引、约束、初始化及持久化数据格式，并非只针对本次共享文件夹升级。[AGENTS.md](../AGENTS.md) 要求在实施前明确并确认具体兼容方案，包括历史字段值的业务含义、数据保留、验证与恢复。这套结构对比升级机制已经确认；新的业务兼容决策仍需单独确认。

## 只维护一个最新目标结构

`packages/db/src/create-schema.ts` 及其结构辅助函数中的最新 DDL 是唯一目标结构。新库创建和旧库升级检查共用 `createCurrentStructure`，普通增量升级不累积逐版本 SQL 迁移脚本，也不按应用版本逐级重建历史结构。

`packages/db/src/schema.ts` 中的 Kysely 类型须与 DDL 一致。`schemaEvolution` 只声明当前支持的兼容代际内已审定的新增表和字段，不保存历史 SQL；写入声明不代表类型变化或数据转换已经安全。仍受支持的旧结构需要这些声明时，不得在未确认支持范围变化前移除。

`schema_baseline.id` 表示兼容代际，不是每次发行的版本号。当前为 `doca-2026-10-12-book-payload-storage-v1`，普通新增表和字段不调整它。既有显式历史存储升级和中断回退检查保留，因为它们改变了持久化历史数据的语义。

目标是让受支持的旧结构直接对齐最新目标，不依赖中间版本的脚本。但代际相同还不够，结构和语义差异也必须符合已确认策略，不能承诺任意历史库或手工修改的库均可升级。重大不兼容变化须先确认拒绝范围、必要的显式转换、数据保留与恢复方案，再决定是否建立新代际。

## 启动时对比与处理

启动先取得数据库或 schema 的结构锁，再比较已安装结构与最新 DDL 生成的参考结构。检查覆盖字段、类型、默认值、是否允许空值、主键、外键、唯一和检查约束及索引。PostgreSQL 使用会话临时参考表，SQLite 使用独立内存库，参考结构不会使用用户文档。

PostgreSQL 通过 `pg_attribute.attnotnull` 校验字段空值约束。PostgreSQL 18 还会在 `pg_constraint` 中记录字段 `NOT NULL`，表约束比较须排除这份重复记录，避免把已审定的必填字段新增误判成额外约束变化。已确认的字段对齐策略允许在校验旧行后，用原生 ALTER COLUMN 对齐空值约束；主键、外键、唯一和检查约束变化仍需确认。参见 PostgreSQL [18](https://www.postgresql.org/docs/18/catalog-pg-constraint.html) 和 [17](https://www.postgresql.org/docs/17/catalog-pg-constraint.html) 的目录说明。

| 差异 | 启动行为 |
| --- | --- |
| 空数据库 | 按最新结构创建，并初始化系统记录。 |
| 已审定且缺少的表 | 创建表及声明的索引，不推断或补造历史记录。 |
| 已审定的可空字段，或具有已确认字面量默认值的必填字段 | 扩展字段，为已有行补齐已确认的历史值。 |
| 已有表缺少普通非唯一索引 | 创建索引并复核结构。 |
| PostgreSQL 同类型 varchar 长度扩大，或已有字段默认值、空值约束不同 | 原生 ALTER COLUMN 对齐；旧值不改，改为必填前校验不存在 NULL。 |
| SQLite 空值约束不同 | 使用内置 SQLite 3.53.4 的原生 ALTER COLUMN，先校验旧行；不替换表、不关闭外键。 |
| SQLite 默认值不同；类型转换、长度缩小；主键、外键、唯一或检查约束、索引定义变化 | 报告待确认计划，在持久化修改前停止。 |
| 必填字段没有已确认的历史值；已有表新增唯一索引；重命名或删除；未知表；持久化业务语义变化 | 需要另行确认数据保留或转换方案，不静默执行破坏性或语义升级。 |

新增字段必须说明它对已有行的业务含义，以及如何保留原有行为。新建记录的默认值和历史记录的补充值可以不同；对比器不能自行猜测。权限、分享、凭证和资源限制不能因为给旧记录补一个方便的值而被静默放开。重命名须按数据保留处理，不能伪装成删掉旧字段再新建字段。

SQL 结构相同时，对比器无法检测 JSON 格式或业务含义变化。开发者仍须评审这些兼容决策，实施已确认的校验、转换或代际检查，不能用结构对比通过来证明语义兼容。

升级成功后，`schema_baseline.structure_json` 只记录最新已安装的表和字段清单，替换旧清单，不累积迁移历史。曾经安装的表或字段丢失时，应按可能的数据丢失报告，不能当成新字段自动重建并重置配置。插件业务表现已存放于[共享插件业务库](plugin-database-isolation.zh-CN.md)。残留旧 `plugin_<56位十六进制>` 表作为未知表要求审查：启动保留数据并在持久化结构变更前停止。须先在旧宿主正常卸载再升级，不自动删表或迁移；插件业务数据版本继续使用自身公开存储约定。 0.1.26 使用与核心库分开的[插件共享业务数据库](plugin-database-isolation.zh-CN.md)，宿主格式 3 取代已发布 0.1.25 格式 2；有效旧安装在持久化写入前被拒绝，须先在旧版正常卸载再重装，不迁移私有数据。核心 DDL 和兼容代次不变。

先分类整个升级计划，再执行持久化 DDL。只要其中一项需要确认，本次就不执行其他自动项。检查、已接受的修改、结构复核和最新清单记录都在结构锁保护的事务中完成，任何失败整体回滚。重复启动须保留原数据和用户设置；记录的结构清单损坏时也停止启动。系统不提供通过删库、重置数据或跳过检查来强行升级的方式。

PostgreSQL 获得结构锁后须读取最新目录，让并发宿主能看到前一个已提交的升级结果，不能使用等待锁之前的旧快照。

## 已确认的原生字段对齐（0.2.10）

用户已确认 PostgreSQL 可自动扩大同类型 varchar 长度，并对齐最新 DDL 的默认值及空值约束；SQLite 仅用原生 ALTER COLUMN 对齐空值约束，默认值变化仍停止启动。不重建或替换表，不直接编辑 writable_schema，不补造旧值，不自动降级。后续当前 DDL 涉及历史业务语义的变化仍须事先确认。核心策略显式启用字段对齐，严格结构校验和现有知识册离线转换门槛保留各自策略。

持久化 DDL 前先分类整个计划；PostgreSQL 在校验旧值前锁定受影响的表，SQLite 沿用已有写事务和结构锁。有 NULL 无法改为必填、任何不支持的差异、未知 SQLite 触发器或视图、复核失败，都会拒绝本次全部修改，包括其他已允许的字段、表和索引新增。字段对齐与最新结构清单在同一事务提交。修改默认值不改已有行；移除 NOT NULL 不代表允许修改主键、外键、唯一或检查约束。排序规则、identity 和生成列属性不属于自动处理范围。

PostgreSQL 的 assets.purpose 最新目标是 varchar(32)，以保存现有 18 字符 ai_image_candidate；SQLite 保持原 varchar(16) 声明，SQLite 本身不按此声明限制长度。新库和 PostgreSQL 临时参考目录共用相同的引擎目标 DDL。启动可将已发布库的 varchar(16) 无损扩到 32；已安装长度更大、需要缩小的结构仍拒绝。不删除或截断旧值，兼容代际不变。

发布验证使用已发布 0.2.9 源码 655e7ecf71274417d2cf5f352f9151612c702859 创建 SQLite、PostgreSQL 17/18 隔离库，131 张原表的数据哈希全部保留。PostgreSQL 目录仅 purpose 长度 16→32；SQLite 结构不变。独立回归覆盖原生默认值/空值约束处理、父子表数据、SQLite 根页与行号不变、重复/并发执行、有 NULL、类型变化、缩小和未知对象拒绝，以及事务回滚。详见[发行核验](verification/ui-image-ark-plan-2026-10-23.md)。部署前备份并统一更新所有宿主；不引入自动降级或混合版本保证。

## 后续开发与发布流程

1. 明确受影响的旧版本、兼容代际、代码路径、已有数据及持久化格式。说明哪些差异保留、新增、拒绝或显式转换，列出历史值、验证和恢复方案，按仓库兼容规则取得确认。
2. 修改最新 DDL 和对应类型，只在 `schemaEvolution` 中声明已审定、对比器支持的新增项。语义转换使用另行确认的机制；普通升级继续共用目标结构与对比器。
3. 为受影响旧结构补充或调整隔离回归样本，包含代表性的已有行。检查原值保留、新字段默认值、适用时的新表为空、重复与并发启动、需确认或验证失败时结构和数据均未被部分修改，以及曾安装字段丢失时不能被静默重建。
4. 执行 SQLite 结构回归和 PostgreSQL 17、18 矩阵。`.github/workflows/database-upgrade.yml` 已执行 PostgreSQL 结构和文件夹用例；后续业务改动须增加自己的相关用例。SQLite 通过不能替代 PostgreSQL 验证，从最新结构反向删字段也不能单独证明实际旧版本可升级。
5. 发布前使用受影响的已发行旧版本创建隔离数据库，再用候选版本升级。验证业务数据保留、受影响功能和升级后的重启，将实际覆盖的版本、数据库引擎及重要限制记入发行验证和升级说明。

使用合成账号和隔离测试数据库、文档。`tests/database.ts` 为每个 PostgreSQL 样本创建并清理独立 schema，不得在用户库上运行破坏性样本或协同编辑测试。涉及协同或插件契约的改动还须遵守相应专项约定。

本规范、中英文版本和实现须同步。新增自动处理行为、支持范围变化及语义例外应一起完成确认、实现、文档和验证。文档中的未来能力说明不代表当前对比器已经支持。

## 部署与恢复

已获同意的[知识册批次检查点](knowledge-book-generation-performance.zh-CN.md)通过最新 DDL 和 `schemaEvolution` 新增空的 `knowledge_book_batch_checkpoints` 表，保持 `doca-2026-10-12-book-payload-storage-v1` 代际。既有 node/run/release 行、引用约束、v1 格式、权限和发布指针不变，不猜测或回填历史结果。独立的私有检查点 v1 格式严格校验。[验证记录](verification/knowledge-book-checkpoints-2026-10-19/README.md)覆盖实际已发布 0.2.3 在 SQLite、PostgreSQL 17/18 创建的数据升级、记录及正文字节保留、重复/并发启动和拒绝时无部分写入。所有执行器与垃圾回收实例一起更新；旧二进制无法保护新的检查点引用。存在检查点时，离线正文存储回滚会在修改前停止，需另行批准保全方案。

部署前备份数据库。启用新文件夹限制前须更新所有宿主实例：旧宿主不执行新的人数限制和邀请确认，不能混用新旧版本。这个已审定的增量变化无需调整兼容代际，也无需离线迁移命令。

保留原数据库与文件卷、部署身份和 `DOCA_CREDENTIAL_MASTER_KEY`。结构增量兼容不自动代表可以混用新旧应用或安全降级，应按实际业务行为评估。

启动升级失败时，事务保留原结构和原数据。成功升级后若要恢复旧应用行为，须单独确认数据保留与恢复方案；恢复升级前备份会丢失之后的写入，应先保留新增记录。不要删除数据库来绕过待确认差异。

已有隔离验证覆盖 SQLite 和 PostgreSQL 17、18 的旧结构及已有数据、空的新表、可空和必填默认字段、重复与并发启动、默认值及空值约束变化、插件数据保留、已安装字段丢失拒绝。0.1.22 还使用实际 0.1.20 镜像创建 PostgreSQL 18 旧库后再升级。文件夹用例覆盖通知、工单、确认授权、实时权限、过期和并发名额校验；这些记录不替代未来改动自己的验收。
