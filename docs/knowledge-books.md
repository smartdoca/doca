# Knowledge books

[中文](knowledge-books.zh-CN.md)

A knowledge book is a generated, read-only Markdown document tree. Editable documents, libraries, files, folders, web pages and authorized `content.v1` providers are its sources. People maintain its sources, workflow and acceptance rules together. The personal AI assistant uses the same commands and authorization as the interface; there is no separate shared assistant identity or personal memory.

## Work together

Open **Knowledge books**, create a book, and use **Permissions** to invite collaborators. This is the existing document permission panel and role model: readers view, commenters submit feedback, editors maintain configuration and their own source authorizations, managers also manage access and remove other contributors' sources. A contributor alone can change their source scope. Concurrent changes use explicit revisions and return a conflict instead of overwriting another person's work.

A book uses a library resource for authorization. Ordinary document creation, move and copy cannot write into it. The title, permissions and deletion lifecycle remain host-owned. Generated pages are immutable release artifacts, not editable resource documents.

## Configure and run

1. Set the goal, model, first-level classification and maximum document depth.
2. Register sources. Short source lists use cards. Original resource access is checked for every source and descendant; an administrator's authority over the book does not grant authority over a source.
3. Adjust the X6 workflow graph. Drag nodes to arrange it, connect ports or choose inputs in the node panel, and edit rules, source selection, weights and acceptance selection. Saving validates input types, cycles, identifiers, reachability and a single publication node.
4. Define acceptance criteria. Required criteria must pass; every configured criterion must be evaluated before publication.
5. Start the persisted run, inspect node outcomes, and process any human tasks. A queued run is not a completed release.

Node types are source loading, human feedback loading, factual extraction, synthesis, document-tree organization, acceptance, human review and publication. Nodes run on a frozen configuration and input revision. Ordinary runs reject configuration or source changes. Explicitly continuing a failed pipeline uses its frozen configuration even if future runs have different settings; sources and feedback must still match. Source content is revalidated before publication. Unsupported formats, excessive input, incomplete extraction, invalid citations and model truncation fail visibly; there is no silent partial publication.

Book cards expose rename for editors and removal for owners. Removal uses the existing resource trash/restore flow and retains configurations, inputs and releases. The assistant opened from a book carries that book as its current resource; general knowledge-base intent does not override it.

Daily and weekly schedules use UTC periods. Automatic publication is an explicit configuration option; otherwise successful acceptance creates a publication task. A failed run leaves the last published release unchanged and creates a repair task.

It can explain an outstanding approval and wait for the decision; it does not approve for the user merely because a worker notification arrived. Installed plugins can use the same [public continuation service](plugin-ai-continuations.md).

It recovers workers whose fifteen-second heartbeats have been absent for five minutes, wakes registered assistant waits, and delivers in-app failure, review and publication notifications. Pending human tasks are the durable delivery source; keys include the task ID, revision and recipient, so restarts and concurrent instances do not duplicate a notification. The recorded run initiator (if still an editor) and current book managers receive alerts; readers do not. List and unread-count reads recheck book edit access. The visible navigation bell shows the current unread count and updates after reading alerts. Alerts link to the exact task. This is in-app delivery, not an email or device-push integration.

This approved notification addition uses the current `notifications` table and database generation with no new columns or migration. Historical runs, errors, tasks and notifications stay unchanged. Startup delivers still-pending tasks, not resolved/cancelled tasks. Existing strict source-format and database-generation rejection rules remain unchanged. Deploy the matching host and web build together; rollback preserves new notification rows, which an older web build may not label correctly. Existing node checkpoints remain the resume boundary; partial model batches are not persisted as independent checkpoints. Model results and node failure/completion writes recheck the worker lease, preventing late model returns from overwriting a recovered pipeline's completed nodes.

One source card can bind multiple documents, libraries, files, folders, web pages or provider configurations, including mixed types. Only `{version: 1, items: [...]}` is accepted; every binding has a stable `id`. A group has at most 50 bindings, with no duplicates or nesting. Old single-input configurations are rejected without converting historical data. The contributor needs original access to every binding.

The web picker accepts bulk URLs and searches through the configured service, including SearXNG, with optional website constraints. Body validation, active-group saves and workflow source reads use the web reader configured in AI settings (built-in, Firecrawl, Jina or Tavily). Fragment URLs use HTML from the selected reader to verify and extract the exact section; Firecrawl and Jina support this, while Tavily requires a whole-page URL or a reader supporting HTML. Reader failures are reported without switching to another service. Search cards help discover sources; snippets are not evidence. Adding a URL verifies the actual body, selected fragment and size. Saving an active group fetches again on the server; a failed URL does not cause a partial save. Pausing retains configuration without a network check, while reactivation verifies again. Private source addresses, embedded credentials, missing fragments and unreadable pages are rejected; external readers receive only source URLs that pass the host's public-address check.

The same public `content.v1` provider serves native library subscriptions and knowledge books. There is no separate book-specific plugin registry. A group can select different configurations of one provider. Revoked binding or contributor access prevents new ingestion, and result reads still authorize concrete evidence references.

Escape collapses an expanded canvas. Canvas tools are left aligned; hide the node palette separately or hide the full toolbar and restore it with the compact canvas button. Publication remains unique and saving validates the complete workflow.

Click a node on the canvas to edit its settings; duplicate editor cards no longer appear below the graph. Icons, names and descriptions in the left node palette align to the left. Save after making changes.

## Human intervention

All review nodes, publication approvals and failed nodes appear in **Human tasks**, both across books and within a book. Query by task type and status, view the actual candidate content and checks, and approve, reject or continue. Revision checks prevent duplicate resolutions. A stale task cannot approve changed inputs. Repair tasks continue the same frozen pipeline through `resume`; the separate `retry` API creates a new run from current configuration. Changed content reopens downstream human gates with a new task revision. Earlier resolutions, including the actor, note and timestamp, are retained in the host security audit when the same task is resolved again.

Define shared acceptance criteria once and reference them from multiple acceptance nodes through `criterionIds`. Reviews follow the frozen descriptions and explicit exceptions; identifiers such as `grounded` do not impose a built-in Manual-only policy. Explicitly permitted accurate background knowledge must not fail solely because a source omits it. Source-grounded criteria still require evidence, and external-knowledge permission does not excuse arithmetic errors or protocol contradictions. `resume` retains frozen rules; use a new retry to apply changed configuration.

Every acceptance node independently reviews its selected mandatory criteria; failed checks block publication by default. A repair task for completed negative acceptance with valid checks and candidate content offers **Accept known issues and continue**. Enter the known issues being accepted and confirm the candidate. Technical failures, missing content and invalid reviews are ineligible. Original failed checks and the node's failed status remain unchanged. The actor, note, candidate and configuration hashes are audited and included in release provenance. The approved candidate is reused; downstream human gates still run, including publication approval when auto-publication is disabled. `run.publish` alone cannot bypass a repair task.

This approved addition records `acceptanceOverride.version=1` in the existing task resolution. Configuration, workflow and artifacts remain version 1, without SQL changes or historical conversion. Existing resolutions without that explicit decision confer no override. Publication revalidates the approver, source access, input snapshot, live and frozen configuration, and candidate; changes invalidate approval. Deploy matching host and Web builds. Before rollback, stop new execution. Older code can read the same published artifacts and failed checks, but does not recognize the new override and cannot continue its pending publication.

**AI examples** prepare source, criterion and correction requests in the personal assistant for the user to review before sending. **My operation history** lists only the current user’s conversations associated with the book; other contributors’ chats and memory remain private.

Comments, corrections, supplements and questions are versioned workflow inputs. Add them directly or ask the personal AI assistant to register them. Feedback can refer to an immutable release, page and paragraph. Readers need original evidence access to anchor feedback to restricted content. Editing feedback creates an input revision; it never changes the published paragraph directly. Weighting and adoption belong to node rules; a high weight does not make an unsupported assertion true.

## Results and provenance

The default reading view shows the rendered document without feedback actions, evidence counters or decisions. Switch to **Review** to inspect paragraph evidence and submit anchored feedback. The published Markdown and provenance are unchanged by this view setting.

Tree titles wrap to show full chapter and page names, with expansion arrows before the directory title. Selecting a directory opens its first descendant document and expands its path; the arrow only changes expansion. The tree, document and management lists scroll independently.

The reader includes path breadcrumbs, heading styles, an active page outline and previous/next links in directory order. The outline appears on the right when space permits, and collapses above the text in narrow readers. Navigation uses actual Markdown headings, excludes fenced code comments and supports keyboard focus. Articles without headings have no invented paragraph outline; their stored content stays unchanged. New synthesis and organization runs request meaningful second- and third-level headings without rewriting historical releases. The host uses the shipped exmd `MarkdownPreviewInteraction` hook for rendered navigation and preserves original image authorization.

New content generation teaches the supported subject: definitions, components, mechanisms, conditions, exceptions, tradeoffs and examples, with real fenced Mermaid architecture/process diagrams where evidence supports them. Learning guidance is a short introduction rather than the whole result. Synthesis processes at most 40 claims per model request; organization groups bounded page inputs and preserves detail. Coverage checks reject omitted distinct supplied claims, long chapters without headings and organization that removes every supplied Mermaid diagram. Format repairs receive these diagnostics. Large generated chapters split at the current 200-paragraph page limit without discarding content. These checks apply to newly generated output; existing releases are not rewritten.

When a writing request reaches its input context, output character guard or model token limit, the runtime subdivides it at complete claims/paragraphs and combines validated results. Even a chapter with fewer than forty claims can span multiple requests. Truncated or structurally invalid multi-unit JSON is discarded and subdivided rather than repeatedly requesting the same oversized output; indivisible units receive bounded repair attempts and fail explicitly if still invalid. Version 1 configuration/workflow/artifact formats and stored data are unchanged. Per-source, per-response and publication guards remain; the obsolete 120,000-character combined-node ceiling is removed because model inputs are batched. `book_size_limit` is a shared error category, not evidence of a total book byte quota. New errors preserve specific diagnostics in the already-supported presentation `data.detail`; historical generic errors cannot be reconstructed. Large-book storage and remaining limits are evaluated in [the storage assessment](knowledge-book-storage-assessment.md).

Assignment format or coverage failures also subdivide at complete claims. Empty records for known sections do not remove any supplied claim; exact-once coverage still applies before assembly. Planning and assignment repairs request only their own JSON schema.

A structurally valid section with incomplete references or insufficient actual prose receives one whole-scope substantive repair before subdivision. Structural errors and hard budgets still subdivide complete content immediately. For one indivisible claim only, the final bounded repair may retain at least 75% of its estimated allocation as a draft; earlier attempts still target 90%. Whole-book length and depth inspection remains required and counts the actual prose, not the allocation. Fixed chapter names and path lengths are included in the private model output schema and rechecked exactly.

Explicit long-form goals of at least 20,000 characters first plan a compact chapter/section outline from source titles and representative claim samples. Separate requests assign at most 32 claims to those sections; the host verifies every supplied claim exactly once and combines the results, avoiding a single full-book assignment response. This plan is execution-only and adds no configuration or artifact fields. Section writing requests contain at most 12 claims and contribute to fixed chapter titles/paths; organization retains that chapter tree instead of letting each batch expand the directory. Depth is developed through causal derivations, complete worked cases, boundary counterexamples and evidence-based diagnosis as required by the configured goal and criteria. Long-form acceptance inspects smaller chapter fragments (3,000 Markdown characters and 12 referenced claims; an indivisible paragraph is never cut) so protocol and numerical defects are not hidden in a large review context. Each fragment explicitly reports its chapter coverage; summaries combine demonstrated chapter obligations rather than inferring depth from headings, keywords or length. Protocol identity, sender/receiver direction and source-specific algorithms are verified before preserving examples. Acceptance JSON repairs preserve factual failures and require exact criterion IDs. Persisted version-1 formats and historical data remain unchanged.

Extraction, writing, organization and detailed acceptance run at most two independent batches concurrently within a node; failure cancels and drains the other worker. Explicit character goals are allocated across writing branches and batches. Prose counts exclude code and diagram source; diagram counts use actual Markdown code nodes, excluding nested examples. New writing and organization outputs pass the installed Mermaid parser in an isolated worker with a time limit; invalid syntax enters bounded repair. This does not render SVG or rewrite historical releases. Organization rejects more than 10% content compression, including subdivided requests. Acceptance first separates each configured criterion into local and global obligations without adding source teaching objectives as requirements. Total length, complete topic coverage and diagram type presence belong to the whole book; batches inspect present assertions and diagrams only. Acceptance inspects complete paragraphs with their referenced claims and evidence, then evaluates global criteria from host counts, the directory and bounded review summaries; it never resubmits the whole book. Any failed detailed inspection blocks that criterion. Acceptance judges the current candidate independently; stale failure reasons are supplied only to content repair, never to new acceptance judgments. Every configured criterion is checked exactly once. Permissions are revalidated before each vendor call, including global summaries.

The assistant reads the workflow input-type rules before modifying nodes. Same-type writer chains remain invalid; graph errors identify the exact edge. Configuration writes affect future runs: patching a node and calling `run.resume` does not apply the new parameters to the frozen run. Use an explicitly requested new retry for changed configuration.

Results render through the existing read-only exmd preview. The interface shows a document tree, release selector, paragraph feedback controls, adoption reasons and validated source excerpts. It does not expose a Markdown source editor.

The provenance graph is created from actual node outputs. It connects source versions, cited excerpts, factual claims, adoption decisions, paragraphs, pages, execution nodes and the release. Human review decisions are also recorded. It is not a separately editable graph. View the whole graph or the ancestors of a selected page, and click nodes to inspect their evidence. The default display groups excerpts by source and groups claims in the current scope; identical relationships between displayed nodes become one counted edge. Click a group to inspect original members, or disable grouping for individual relationships. This changes the display only, retaining the original artifact and evidence.

Raw source bodies stay in the source system and transient execution memory. Releases and node logs retain only exact cited excerpts, hashes, source references and generated content; they do not maintain another full source-body archive. Native source updates do not rewrite a historical release. Original source permissions are checked when results or node logs are read. External deletion, unbinding or provider unavailability withholds affected results without deleting retained artifacts.

A contributor losing book edit access stops future ingestion. Already generated data is retained; retention does not grant display rights. If any model-context source is inaccessible, the combined result is withheld conservatively, including inputs omitted from model citations.

## Shared API

All routes use `/api/v1/knowledge-books`:

| Route                               | Purpose                                                              |
| ----------------------------------- | -------------------------------------------------------------------- |
| `GET /`, `POST /`                   | List / create books                                                  |
| `GET /:id`                          | Current configuration, sources, feedback, runs and published release |
| `POST /:id/commands`                | Shared human / AI command dispatcher                                 |
| `POST /:id/source-search`           | Search configured web providers after book edit authorization        |
| `POST /:id/source-web-check`        | Verify actual URL bodies and selected fragments                      |
| `GET /:id/runs/:runId`              | Execution and candidate outcomes                                     |
| `GET /:id/runs/:runId/pipeline`     | Authorized canvas projection without full node bodies or provenance  |
| `GET /:id/releases/:releaseId`      | Immutable generated release                                          |
| `GET /human-tasks`                  | Query by book, run, node, query, kind, status and offset             |
| `POST /human-tasks/:taskId/resolve` | Approve / reject / resume / retry with expected revision             |

Commands are `configuration.save`, `configuration.patch`, `workflow.node.patch`, `workflow.node.add`, `source.remove`, `source.save`, `feedback.save`, `feedback.withdraw`, `run.start`, `run.cancel`, `run.resume`, `run.retry` and `run.publish`. Configuration, source and feedback saves require `expectedRevision`. The version 1 schemas in `packages/core/src/modules/knowledge-books/protocol.ts` are authoritative. The AI `knowledge_book` tool delegates to these same functions; personal assistant conversation and memory remain owned by the real user.

## Removal and database boundary

Old library curation and Q&A robots are removed: no curation conversations, workers, settings, instructions, entries or publication projection. Native documents, source subscriptions, indexing and search remain. The library navigation no longer shows the Sources and subscriptions entry; existing subscription records are retained.

Current source uses baseline `doca-2026-10-12-book-payload-storage-v1`. Starting 0.1.24 against released 0.1.22 databases on `doca-2026-10-09-history-storage-v1` automatically reviews/reconciles the structure and records the target generation in one schema transaction. Every business row and publication pointer stays untouched, including old SQL-generated outcomes. Runtime only supports native object references; no old-body adapter, automatic conversion or separate cleanup is added. Retained old outcomes can require manual handling before their book is usable. Existing 0.1.23 object storage data remains unchanged. See [operations and recovery](knowledge-book-storage-verification.md). Knowledge-book target tables remain; retired curation tables and fields stay disabled. Normal startup rejects earlier, unknown and interrupted-conversion baselines. Only the exact preceding history baseline supports the explicit offline history-storage upgrade in the [deployment guide](deployment.md#upgrade-from-0113). Retired file bindings remain stored and inaccessible; the retired curation protocol is not restored. Never delete an existing database to start the new host.

A failed or cancelled run can be continued through `run.resume`. It retains the same run ID and frozen workflow, completed nodes and failure logs. Source registrations, feedback, current original permissions and complete live source inventories are revalidated before continuation, including evidence identifiers, versions and content hashes. Added, removed or changed source content refuses continuation rather than silently mixing inputs. A rejected acceptance check restarts the closest upstream content-writing stage and its descendants, retaining extraction and unrelated branches; earlier checks are passed as repair diagnostics. Repeated failures and worker interruptions reuse the same node/task rows while retaining recorded failure facts and task decisions. Only current version 1 configuration is accepted; this performs no historical-format conversion, database migration or deletion.

When repairing a failed acceptance, organization can start from the reviewed candidate only when its cited claim scope exactly matches the currently authorized upstream scope and duplicate page identities are consistent. This keeps review page IDs meaningful and retains earlier corrections. Review lines with page locators go to their current batch; distinctive code values can locate a missing identifier, while unlocated diagnostics are still reviewed for applicability. Unaffected candidate batches retain their original paragraphs after structural validation instead of being rewritten. Failed detailed checks include the current page IDs for subsequent repair. It still checks current evidence independently and does not treat an old review as proof. Prior candidate bodies are never included wholesale in a model request; completed node and stored version-1 formats stay unchanged.

The existing `run.retry` remains a separate new-run operation. A retry preserves the prior run and only reuses complete node outputs after checking the exact frozen configuration, source registrations, feedback, and complete current source inventories. Source failures and added/removed/changed blocks prevent reuse. Human gates and their descendants are evaluated again. Each reused node records its original run in the security audit and provenance. Every vendor call revalidates contributor grants, including extraction batches and format repairs.

The public view contains rendered results and provenance; it exposes no editable configuration or dummy workflow. Historical releases use the normal document history permission. Provenance can focus on a page or paragraph; execution/context edges can be included separately.

## Payload object storage

Node outputs and run/release artifacts use the existing host private store. Same-book raw JSON strings are pooled by content hash; original bytes and version 1 responses are preserved. Identical run/release artifacts share a root. SQL retains strict references, permission manifests, summaries, object edges and durable upload/cleanup journals. UI/assistant polling uses summaries; expanding a candidate fetches its body. Cache hits still recheck source permissions. Trash retains references; permanent purge releases them and durable cleanup reclaims unreachable objects. See the [implementation plan](knowledge-book-payload-storage-plan.md).

Writing, organization and detailed inspections use cited evidence as anchors to include whole related blocks from the same sources within 160,000 characters. When related context exceeds the bound, nearby original blocks take priority; no block is truncated and unrelated sources are excluded. Selected context receives the same source-access revalidation. Explicit teaching simulations can choose initial values absent from normative examples, but must satisfy protocol constraints and correctly derive fields, states and arithmetic. Fragment inspections cannot add obligations beyond the original criteria or require a complete chapter case in every fragment. Chapter aggregation preserves concrete case and diagnostic observations, rather than generic depth verdicts. Failure summaries reserve space for every failed batch so later chapters remain locatable on resume.

Long-book detail inspections enumerate assertion anchors inside complete reviewed paragraphs. Every assertion ID must receive a verdict: omission, duplication and unknown IDs trigger bounded repair. The host derives existing v1 checks from these verdicts; no new fields are persisted and a positive overall observation cannot override an individual defect. Extracted claims are candidates: conflicts must be explicitly corrected or excluded using original evidence in the body and adoption reason.

Each assertion is inspected once and associated with criterion IDs it violates, or an empty list. Per-criterion observations retain chapter evidence without repeating every assertion list. Passing verdicts remain brief; failures keep concrete calculations or rule conflicts. Verified Doubao Seed 2.1 calls request native JSON object output, followed by strict host validation. Double-escaped objects and reasoning text are not accepted as results; rejected options report an error without silent fallback.

Assertion inspections use whole related normative blocks within 24,000 characters; hints accompany complete paragraphs without replacing or truncating them. Failures identify paragraphs and original assertions. Located paragraph references select repair batches before chapter references, preserving other validated batches. After a syntax failure in new model output, flat square-bracket flowchart labels can be quoted and checked again by the actual parser. Label text, edges and diagram type retain their meaning; complex errors still use bounded model repair. Stored historical artifacts are not automatically rewritten.

Resume binds negative acceptance results to their reviewed v1 pages. If content was already repaired and a later technical acceptance request failed, the retained earlier review does not invalidate the newer completed content: resume reuses it and inspects it again. A negative review of the current candidate still triggers content repair. Earlier diagnostics remain retained; no storage fields or historical error-text adapters are added.

For verified Doubao Seed 2.1 models, substantive extraction, writing, organization and acceptance request native thinking (medium effort, including assertion inspections). Outline and assignment requests keep short outputs. The fixed existing SDK maps the supported options; rejection is an error, with no automatic model switch or silent parameter downgrade. Existing provider Responses/Chat and optional reasoning-summary adaptation is unchanged. Configured models and budgets and the v1 persisted protocol are unchanged.

Within one execution, complete negative assertion diagnostics are retained in bounded memory and reused only when both the candidate-page hash and evidence/claim scope hash match. The compact persisted v1 check summary retains actionable defects and paragraph locations. A technical acceptance retry after content has changed reuses that completed content, rather than applying a stale negative review to it; source and access revalidation still apply. The real-model acceptance harness owns execution before starting its HTTP reader, so background workers cannot claim the test run and bypass its diagnostic observer.

Bounded assertion inspection prioritizes complete blocks containing the current paragraph’s distinctive protocol/field/state terms before nearby blocks. Cited anchors are always retained and no unrelated sources are introduced. Each clause, field count, width and arithmetic result is checked independently.

Numerical item/field-count clauses are also inspected as separate literal excerpts of the same unchanged paragraph. A correct byte sum cannot establish a claimed number of fields. These assertion hints remain execution-only and do not add persisted verdict fields.

Teaching analogies do not establish algorithms, state transitions or diagnostic actions for a different protocol. Such recommendations still require the destination protocol's original evidence; a supported clause about one protocol cannot support an unrelated clause about another in the same sentence.

When an assertion audit has a failed local assessment, the runtime may expand the same authorized source scope from 24,000 to at most 100,000 characters and independently re-inspect the unchanged paragraphs once. Distinctive paragraph and diagnostic terms still rank whole blocks; expansion also supplies original rules when a translated assertion has no matching source-language terms. Expansion does not depend on the language, wording or missing-evidence keywords of a rejection. The configured model input budget remains authoritative. Both attempts remain in diagnostic observations; only the final assessment supplies repair findings. No retry occurs with identical evidence, no required criterion is dropped, and actual contradictory calculations remain rejected. This is additional evidence assessment, not changing a failed verdict to satisfy JSON formatting.

An execution has a finite four-hour deadline so detailed long-book inspections and bounded evidence rechecks can finish. Per-request input/output protections, explicit cancellation, fifteen-second lease heartbeats and five-minute worker recovery remain in effect. Resuming still uses completed nodes as checkpoints; partial batches are not new persisted checkpoints.

Transient vendor/transport errors, including SDK processing failures on a successful HTTP response and streams without a completion receipt, retry the same scoped request within the existing three-call limit. Partial stream text is discarded, source access is revalidated and cancellation remains authoritative. Rejected parameters, authentication/permission failures and payload capacity errors are not retried as transient failures. No model, parameter or response-protocol fallback is introduced.

When a v1 check summary exceeds 4,000 characters, it retains actionable causes and unique paragraph locations from up to 24 evenly distributed failed scopes, including the first and last, and explicitly counts omitted failed scopes. Omitted entries still block acceptance; complete candidate-bound diagnostics continue to guide same-execution repairs when within the memory bound. Historical summaries are not rewritten.

Evidence lookup retains exact identifiers and also matches their spaced, hyphenated and camel-case components, including numbered event prefixes. This retrieves the same normative event under common prose spellings without changing source text or source permissions.

Fragment inspection includes up to 6,000 characters of whole neighboring paragraphs (two on either side) to resolve preceding definitions and following figures without expanding the audited assertions. Access is revalidated for the full original evidence scope. Present Mermaid syntax is checked by the actual parser; valid equivalent syntax cannot be rejected just for spelling, while a genuine syntax failure blocks relevant configured diagram/format criteria. Syntax success never overrides semantic failures.

Intermediate acceptance aggregation consolidates at most twelve reviews and their chapter identities under an explicit partial scope. The whole-book goal does not become an obligation of that group; absent chapter groups are deferred, while every reported failure or contradiction is retained. Final acceptance still receives the original criterion, complete directory, metrics and all chapter summaries. Successful partial aggregation cannot waive a chapter requirement.

Quantity-clause hints retain Chinese ordinal prefixes and their spacing, so the fourth lost packet is not turned into four lost packets. Complete original paragraphs remain the inspection context; hint extraction rewrites neither the body nor historical acceptance records.
