# User groups and group permissions

[简体中文](user-groups.zh-CN.md)

The sidebar below Shared folders lists joined groups with their avatar, name and owner. Members see the complete roster and roles. Internal group IDs are not displayed as page information.

Owners and administrators invite people through the existing user directory or seven-day invitation links. Joining requires signed-in consent and creates an ordinary member. Sharing a valid group adds a relationship to the existing related-user directory mode. Invitation acceptance checks the issuer's current role and account status. Link tokens are stored as hashes and can be revoked/replaced.

Only the owner appoints/removes administrators, transfers ownership or dissolves the group. Administrators invite and remove ordinary members, but cannot manage other administrators or the owner. Owners transfer to an existing active member before leaving; others can leave directly.

Documents, libraries and knowledge books share host resource permissions. Shared folders and their files also receive group permissions. Invite collaborators has Person and Group tabs with name search/selection above the permission field. The members page manages existing personal/group grants without displaying a new-grant search form. Plugin-owned permission adapters do not automatically gain group APIs.

Each active group grant previews three active members as avatars. Hovering or activating an avatar opens the existing user profile card. More (+count) opens a paged avatar popover without increasing the grant row height. Every roster read rechecks resource management access and the current group grant; an unaccepted new group invitation reveals no roster. Roster responses contain only display identities and avatar fields; profile cards use the existing profile endpoint without opening foreign group management.

Personal and group grants share a compact two-line row: avatar and name on the first line, with the permission selector and delete icon on the right; account/source metadata or group member avatars share the second line with descendant scope. Personal rows include a source-list entry. Deletion uses a confirmation bubble beside the button. Cancel does not write, and failure preserves the bubble and page. Libraries and contained documents allow separate descendant-scope changes; role edits preserve the current scope. Library management floors remain read-only on child documents, and resource managers cannot modify management grants.

Personal and group sources remain independent, taking the highest effective role as explicitly confirmed. Group-only collaborators can receive a personal grant; without a personal source, revoke access through the corresponding group row. When another source exceeds the personal role, the row shows the effective role. Source lists include ownership, personal, inherited, link and group grants. Ordinary inherited personal access can be overridden or revoked on the document; library management floors retain their existing rules. Shared folders retain their aggregated personal share records: link-admission markers annotate that personal source, and groups are listed separately. Historical personal/link records are not artificially split. Only resource managers can enumerate group-derived collaborators.

Group grants stay separate from personal grants and are evaluated against current active membership with inheritance boundaries and scope. All members receive the granted resource role regardless of their group role. Only resource owners assign/change management grants. Existing invitation policies apply: new/increased access requires group owner/administrator acceptance in invitation mode, rechecking the issuer and current members' admission restrictions.

Leaving, removal and dissolution immediately invalidate that source; independent access remains effective. Connected collaboration sessions are reauthorized. Search/knowledge projections refresh, and knowledge results check current access before returning. Ownership transfers preserve group grants; declining retained personal access does not remove group access. Disabled-account handover includes owned groups and requires the recipient to already be an active member, with a fingerprint guarding preview/execution changes.

Administrators configure an independent group directory policy with per-user overrides. Initial scope is joined groups only. Other scopes add groups with intersecting explicit document/library/shared-folder access, or all active groups. Effective inheritance counts; public visibility does not. Search returns basic metadata without opening a foreign group member page. After a group receives resource access, its members become resource collaborators: resource managers can see effective collaborators, and the user directory applies the existing shared-explicit-permission relationship. New grants validate selection scope again on the server. Scope reductions preserve existing grants/invitations and allow their removal. Cursors bind actor, query and policy revision.

Dissolution marks the group inactive transactionally. Startup/hourly cleanup removes associations for groups dissolved for at least 24 hours, at most 100 per batch. Memberships, invitations, links and group grants are removed; group tombstones, audit records, content and personal permissions remain.

The approved upgrade adds eight tables through latest target DDL and `schemaEvolution`, retaining the compatibility generation. Seven group/ACL tables start empty; the independent policy explicitly initializes `system/member/revision=1` on first installation. No historical personal/link grants, invitations, public settings or user directory policies are converted. A missing installed policy row is not silently recreated. Back up data, files and configuration, and update every server and Web together. Downgrade needs separate preservation/recovery review. See [verification](verification/user-groups-2026-10-30.md).
