# 知识册大篇幅生成：性能改动与批次续跑

[English](knowledge-book-generation-performance.md)

2026-10-19。批次检查点已获得用户明确同意并实施，当次使用隔离数据验证，未部署生产。

## 已实施的执行优化

- 长文按节写作在请求前参考配置模型的输出预算拆分，每批仍最多 12 条判断。完整字数配额按判断分配，不截断正文、代码或图，不放弃引用。单条判断不可再分时，仍使用现有有限补写和失败规则。输出预算是估算，无法保证供应商永不截断。
- 独立的分层质量汇总复用现有两路并发池，结果按原分组顺序交给最终检查。任一请求失败时取消并等待另一请求结束。
- 单条质量观察直接保留原结论、章身份和原因，不再发送一次内容相同的汇总请求。多条观察仍经汇总，局部失败继续阻止验收，最终整册检查继续执行。
- 第一轮执行优化未改变存量格式；本轮按已同意方案新增检查点表和私有对象引用。配置、已发布成果及历史节点输出的 version 1 保持不变。

在隔离模型响应测试中，25 个质量批次产生的三个汇总组由三次串行模型请求变为两次并发请求加一条原样保留的观察。该结果仅证明这一汇总层少一次请求、少两个串行等待轮次，不能外推为整册快 3 倍。

用户描述的 15 万字、约 8 小时任务位于线上，本地没有该运行的日志。尚未复现线上失败、质量误判或总耗时，也没有用线上数据进行写入或重跑。

## 原有浪费与本次范围

此前只在完整节点完成时保存输出，节点中途失败会重做未落盘的批次。本轮新增完整请求结果、规划和分配的持久化。候选修复仍受当前授权与内容范围约束；新增批次检查点不跨运行复制，也不复用发生变化的范围。

已发现的节点复用、冻结运行继续和历史成果读取规则保持现状，本次不新增旧成果适配器、不转换历史运行、不调整质量门槛。完整节点输出仍使用既有原生对象引用；历史 SQL 正文的现有人工处理边界不变。

## 已同意并实施的具体方案

适用当前 `doca-2026-10-12-book-payload-storage-v1` 兼容代际中、结构检查合格的数据库；不承诺任意历史数据库升级。配置和已发布成果继续使用现有 v1 协议。

1. 新增独立表 `knowledge_book_batch_checkpoints`，保存知识册、运行、节点运行、阶段、计划哈希、批次键、输入哈希、结果对象引用、创建时间；唯一键覆盖节点运行、计划哈希及批次键。按项目的 `createCurrentStructure` / `schemaEvolution` 声明空表，既有行无需默认值或转换，不增加逐版本迁移链，不提升兼容代际。
2. 检查点正文使用独立的 `knowledge_book_batch_checkpoint_ref` v1 引用及对象存储，不把大段正文直接存 SQL，不伪装成已完成节点。对象登记、引用固定和垃圾回收必须识别新的检查点所有者；不得影响既有 node/run/release 引用及内容。
3. 只保存完整且通过当前阶段结构、覆盖、引用和图语法校验的结果；不保存半截流响应。质量检查可以保存完整的否决结论，否决不是失败批次丢弃的理由，也不能被复用成通过。
4. 计划检查点包括冻结目录/分配；写作、编排与逐项验收按照确定的批次键保存。复用前完整匹配冻结配置、所有输入/来源版本与内容清单、当前候选内容、阶段算法版本、模型非秘密配置指纹和请求范围，并重新核验来源权限。模型凭据不写入检查点。内容修复、变更输入或模型配置不能借用旧结果。
5. 老运行无批次记录时继续使用现有完整节点检查点；执行尚未完成的节点时才开始记录新批次。不从日志或旧输出猜测哪些批次已完成，不批量回填或转换历史数据。完整旧节点及发布指针原样保存。
6. 检查点格式未知、内容校验失败或应有对象丢失时明确停止，保留证据供处理；不得悄悄跳过检查点重算来掩盖数据丢失。显式内容修复建立独立范围并保留旧记录，不借用旧结果；相同范围的模型或算法变更要求新建运行，不自动转换旧检查点。
7. 写入由运行租约保护，校验租约、登记对象与安装引用保持一致；取消后不继续安装结果，多实例不能同时覆盖检查点。最终节点聚合仍执行全覆盖校验并安装现有完整输出，发布仍走现有权限和必需质量检查。
8. 初版只在原运行内继续，暂不把批次跨运行复制到新重试。既有新重试的完整节点复用规则保持原范围，不扩大旧运行的授权范围。

## 数据保全、验证与恢复

- 上线前备份数据库及对象存储，暂停执行器，完成所有实例更新及结构检查后再启用检查点；不支持混合新旧执行器同时使用该功能。
- 验证保留真实旧行的隔离 SQLite、PostgreSQL 17 / 18：空表增补、重复/并发启动、结构差异拒绝且无部分写入；还需使用实际已发布旧版本创建的数据做升级验证。
- 执行验证覆盖中途断流/进程退出/超时/取消/租约丢失后的续跑、恰好一次安装、权限撤销、来源和模型变化、未知版本/损坏/丢对象拒绝、负面验收保留、不可复用范围与最终发布门槛。
- 已保存对象随检查点引用固定；不能因节点尚未完成被回收。删除知识册沿用现有明确删除流程；不因失败、升级或哈希不匹配清除用户数据。
- 出问题时先暂停执行器并在当前版本停用批次续跑，保留检查点及对象引用固定，修复后再继续。需要整节点重新执行时由用户显式发起；旧检查点保留供核对。降级到旧二进制或恢复备份需另行核对新增数据和对象保全，不自动删表、还原或覆盖上线后的写入。

此方案已按仓库 AGENTS.md 的兼容规则取得用户明确同意。实现与验证范围见下文，不能外推为线上耗时保证。

## 实现与验证

- 新表增加节点范围哈希 `scope_hash`、请求和计划哈希、独立引用及授权元数据。原有 node/run/release 引用约束没有变化。内部 `evidenceInventory` 只保存来源版本、定位、内容哈希、实际权重和权限引用，不复制来源全文。模型指纹不含 API 密钥、别名和费率。
- 完整的宿主拆分计划也会保存，避免恢复后再次支付已知超限的父请求；不保存截断响应。原文修复通过既有显式继续流程建立新内容范围，保留但不复用旧范围。相同内容范围的模型或算法变更要求新建运行。
- `DOCA_BOOK_BATCH_CHECKPOINTS=off` 可在当前版本停用恢复而保留记录及对象保护。已有检查点时，原存储格式回滚在修改前拒绝，需另行审定保全方案。
- 隔离完整流水线测试中，两批写作的第二批失败；更换整个运行时继续后，累计写作请求由 2 次增至 3 次，第一批没有重做，42 条判断全部保留并走完验收和发布。另覆盖长文规划/分配、否决诊断及超限拆分计划恢复。
- 真实文件存储测试在第一批提交后向进程发送 SIGKILL；新进程换租约后读取冷存储，原批次调用为 0、缺失批次调用为 1，两条检查点均受到回收保护。
- 使用实际已发布的 `smartdoca/doca:0.2.3` 镜像创建 SQLite、PostgreSQL 17/18 数据后升级，13 组既有表记录指纹、节点/运行/发布正文 SHA-256、发布指针和兼容代际均保持一致；新表为空。重复/并发启动及差异拒绝无部分写入另有回归。
- 详细结果见[隔离验证记录](verification/knowledge-book-checkpoints-2026-10-19/README.md)。
