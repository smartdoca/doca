# Database upgrade contract

[简体中文](database-schema-evolution.zh-CN.md)

The approved user-group addition retains this contract and compatibility generation: seven empty group/membership/invitation/ACL tables plus an independent directory policy explicitly initialized to joined groups only (`system/member/revision=1`). User overrides start empty. Historical personal/link grants, invitations, public settings and user directory policies remain unchanged, without conversion or per-member grant materialization. Installed configuration rows are not silently recreated. Update all servers and Web together; downgrade needs separate preservation/recovery review. See [group rules](user-groups.md), [release notes](releases/0.2.28.md) and [SQLite/PostgreSQL 17/18 verification](verification/user-groups-2026-10-30.md).

This is Doca's project-wide contract for future core database changes. Development and review must follow it; it is not limited to the shared-folder release. Read it before changing tables, fields, indexes, constraints, initialization or persisted data formats. [AGENTS.md](../AGENTS.md) requires the concrete compatibility plan to be agreed before implementation, including the meaning of historical defaults, data preservation, validation and recovery. The reconciliation mechanism below is already agreed; each new business compatibility decision still needs its own agreement.

## One current target structure

The latest DDL in `packages/db/src/create-schema.ts` and its structure helpers is the only target structure. Fresh creation and upgrade inspection use `createCurrentStructure`; there is no sequence of per-release SQL migrations for ordinary additive changes.

Keep the corresponding Kysely types in `packages/db/src/schema.ts` consistent with this DDL. `schemaEvolution` is the allowlist of reviewed table/column additions within the supported compatibility generation, not a collection of historical SQL scripts. Adding a declaration does not make a type change or a data conversion safe. Do not remove declarations needed by a still-supported old structure without agreeing on the resulting support change.

`schema_baseline.id` identifies a compatibility generation, not every release. The current generation is `doca-2026-10-12-book-payload-storage-v1`. The approved [knowledge-book schema alignment](knowledge-book-payload-storage-plan.md) lets 0.1.24 startup align released `doca-2026-10-09-history-storage-v1` databases through the ordinary current-DDL reconciler, then record the target generation in the same transaction. All existing business rows, including old SQL book outcomes and publication pointers, remain untouched. There is no automatic body conversion, cleanup or legacy runtime reader; leftover old outcomes require manual handling. The generation records the installed target structure and does not establish readability of old JSON. Existing optional offline byte-exact maintenance remains available before startup when those outcomes must be preserved in the native object format. Existing explicit history and interrupted-conversion gates remain.

The goal is to upgrade directly from a supported older structure to the current target without replaying intervening release scripts. A matching generation alone is insufficient: structural and semantic differences must also meet the agreed policy. This does not promise upgrades from every historical or manually modified database. A major incompatible change may introduce a new generation only after agreement on rejection, any explicit conversion, preservation and recovery.

## Startup reconciliation

Startup acquires a database/schema lock and compares the installed structure with a reference built from current DDL. Inspection covers columns, types, defaults, primary/foreign/unique/check constraints and indexes. PostgreSQL uses session-local temporary reference tables; SQLite uses a separate in-memory database. Neither reference uses user documents.

Column nullability is checked through `pg_attribute.attnotnull` on PostgreSQL. PostgreSQL 18 additionally records table-column `NOT NULL` constraints in `pg_constraint`; these duplicate entries are excluded from the table-constraint comparison. This allows approved required-column additions without treating their new `NOT NULL` entries as unrelated constraint changes. With the approved column-alignment policy, existing nullability can be aligned using native ALTER COLUMN after validating existing rows; primary/key/check constraint changes still require review. See the PostgreSQL [18](https://www.postgresql.org/docs/18/catalog-pg-constraint.html) and [17](https://www.postgresql.org/docs/17/catalog-pg-constraint.html) catalogs.

`schemaEvolution` declares reviewed new tables and fields. Nullable additions and required fields with literal historical defaults can be added automatically when explicitly declared. New ordinary indexes can also be created. A default expresses a historical business decision; it must never be invented by the reconciler. Required new fields without such defaults, unsupported type/default/constraint changes, unique-index validation, removals and unknown objects produce a concrete `SchemaReviewRequired` plan before any persistent change is applied. There is no automatic deletion or reset.

| Difference | Startup behavior |
| --- | --- |
| Empty database | Create the current structure and initial system rows. |
| Reviewed missing table | Create the table and its declared indexes; no historical backfill is inferred. |
| Reviewed nullable column, or required column with an approved literal default | Add the column; existing rows receive the agreed historical value. |
| Missing ordinary non-unique index on an existing table | Create the index and recheck the structure. |
| PostgreSQL varchar length increases, or an existing default/nullability differs | Align using native ALTER COLUMN; retain all old values and validate no NULL before tightening. |
| SQLite nullability differs | Align with native ALTER COLUMN on the bundled SQLite 3.53.4; validate old rows first. No table replacement or foreign-key disabling. |
| SQLite default differs; type conversion/length reduction; primary/foreign/unique/check constraint or index definition differs | Report a review plan and stop before persistent changes. |
| Required column has no approved historical value; new unique index on an existing table; rename or removal; unknown table; persisted business semantics change | Require a separately approved preservation/conversion plan; do not silently apply a destructive or semantic upgrade. |

For existing rows, explain what a new field means and how its value preserves prior business behavior. New-record defaults and historical-row defaults can differ. Permission, sharing, credential and resource restrictions must not be silently released by filling an older row with a convenient value. A rename must be reviewed as data preservation, not disguised as dropping and recreating a field.

Structural comparison cannot detect a changed JSON format or business meaning when the SQL structure stays identical. Developers must still review those compatibility decisions and implement the agreed validation/conversion or generation gate. A clean structural comparison is not evidence of semantic compatibility.

The latest installed table/column footprint replaces `schema_baseline.structure_json` after successful reconciliation. A previously installed table or field going missing is reported as possible data loss, even if its original introduction was automatic. Plugin business tables live in a [shared business database separate from core](plugin-database-isolation.md). Host storage format 3 replaces released 0.1.25 format 2; active old installations are rejected before persistent changes and must be normally uninstalled on the previous host, then reinstalled without private-data migration. Core DDL and compatibility generation are unchanged. Remaining old `plugin_<56 hex characters>` tables are review-required unknown tables: startup preserves them and stops before structural changes. Complete normal uninstall on the previous host before upgrading; there is no automatic deletion or data migration. Plugin business data versions still use their own public storage contract.

All accepted changes and footprint recording are transactional and rechecked before commit. A failed operation rolls back the whole attempt. Repeating startup preserves data and configured values. Review-required differences need a separately approved data-preservation/conversion plan; startup does not offer a destructive bypass.

The whole plan is classified before any persistent DDL is applied. If one difference requires review, none of the otherwise automatic changes are applied in that attempt. PostgreSQL takes fresh catalog reads after obtaining the schema lock so concurrent hosts see the preceding committed upgrade. An invalid recorded footprint also stops startup.

## Approved native column alignment (0.2.10)

The owner approved PostgreSQL widening of the same varchar type and synchronization of current-DDL defaults and nullability. SQLite only synchronizes nullability through native ALTER COLUMN. Its unsupported default changes stop startup; there is no table rebuild, writable_schema edit, value backfill or automatic downgrade. Future changes to historical business semantics still require agreement before changing the current DDL. The core policy explicitly enables alignment; strict inspection and the existing offline book-storage conversion gates retain their own policies.

Every difference is classified before persistent DDL. PostgreSQL locks affected tables before checking old rows; SQLite uses the existing write/schema transaction. A NULL that prevents NOT NULL, an unsupported difference, unknown SQLite trigger/view, or failed reinspection rejects the entire attempt, including otherwise approved additions/indexes. All accepted attributes and footprint recording commit together. Existing defaults never rewrite old rows, and dropping NOT NULL does not change a primary/foreign/unique/check constraint. Collation, identity and generated-column attributes are not authorized for automatic changes.

The PostgreSQL current target for assets.purpose is varchar(32), enough for the existing 18-character ai_image_candidate value; SQLite keeps its varchar(16) declaration, whose length it does not enforce. Fresh creation and temporary PostgreSQL reference catalogs use the same engine-specific current DDL. Startup can now widen released PostgreSQL varchar(16) without deleting/truncating rows; any larger installed width that would require shrinking is rejected. The compatibility generation remains unchanged.

Verification creates isolated databases using released 0.2.9 source commit 655e7ecf71274417d2cf5f352f9151612c702859, preserving all 131 original table hashes on SQLite and PostgreSQL 17/18. PostgreSQL catalog differences are limited to purpose length 16→32; SQLite is unchanged. Separate regressions cover native nullability/default behavior, parent/child rows, unchanged SQLite root pages/rowids, repeated/concurrent execution, NULL/type/shrink/unknown-object rejection and transaction rollback. See the [release evidence](verification/ui-image-ark-plan-2026-10-23.md). Back up before deployment and keep every host on the same release; no automatic downgrade or mixed-version guarantee is introduced.

## Required development and release workflow

1. Identify affected old versions, schema generation, code paths, stored rows and persisted formats. Explain which differences are retained, added, rejected or explicitly converted, including historical values, validation and recovery; obtain agreement under the repository compatibility rule.
2. Update the latest DDL and matching types. Declare only approved supported additions in `schemaEvolution`. Route semantic conversion through its separately approved mechanism; ordinary upgrades must continue to use the shared target and reconciler.
3. Add or adjust isolated regression fixtures for affected old structures containing representative existing rows. Verify retained values, new defaults, empty new tables where applicable, repeated/concurrent startup, and unchanged data/structure when review or validation prevents upgrading. Check that previously installed fields cannot be recreated silently after loss.
4. Run SQLite reconciliation regression and the PostgreSQL 17/18 matrix. `.github/workflows/database-upgrade.yml` runs the PostgreSQL schema and folder cases; new business changes must add their own relevant cases. A SQLite pass alone does not establish PostgreSQL compatibility, and reversing the latest schema alone does not establish an actual released-version upgrade.
5. Before release, create an isolated old database using the affected released version and upgrade it with the release candidate. Check retained business data and the affected feature after upgrade and restart. Record the tested versions, database engines and material limits in release verification and upgrade notes.

Use synthetic accounts and isolated test databases/documents. `tests/database.ts` creates and cleans an isolated PostgreSQL schema for each fixture. Never run destructive fixtures or collaboration editing checks against user data. Read the applicable collaboration/plugin contracts when a change enters those areas.

The contract and its Chinese version must stay aligned with the implementation. New automatic behavior, support changes and semantic exceptions must be agreed, implemented, documented and validated together. A document describing a future capability is not proof that the reconciler supports it.

## Deployment and recovery

The approved [knowledge-book batch checkpoint addition](knowledge-book-generation-performance.md) adds `knowledge_book_batch_checkpoints` empty through current DDL and `schemaEvolution`, within `doca-2026-10-12-book-payload-storage-v1`. Existing node/run/release rows, reference constraints, v1 formats, permissions and publication pointers are unchanged; no old results are inferred or backfilled. The separate private checkpoint v1 format is strictly validated. The [verification record](verification/knowledge-book-checkpoints-2026-10-19/README.md) covers actual released 0.2.3 data on SQLite and PostgreSQL 17/18, retained rows/body bytes, repeated/concurrent startup and rejection without partial writes. Upgrade all executors and garbage collectors together; older binaries cannot protect new checkpoint references. Existing checkpoints block offline body-storage rollback until a separate preservation plan is approved.

Back up the database before deploying. Update every host instance before enabling new folder sharing restrictions: older code does not enforce the new limit or consent flow, so mixed-version operation is not supported. No compatibility-generation bump or offline migration command is needed for this reviewed additive change.

Preserve the database/file volumes, deployment identity and original `DOCA_CREDENTIAL_MASTER_KEY`. A structurally compatible additive upgrade does not by itself establish safe mixed-version operation or application downgrade; assess those against the affected business behavior.

For a failed startup upgrade, the transaction retains the original structure and data. After a successful deployment, returning to old application behavior needs a separately reviewed recovery plan: restoring a pre-upgrade backup also loses later writes, and old hosts cannot enforce new restrictions. Preserve any new records before such a rollback. Do not delete the database to resolve a review-required difference.

Verification uses isolated SQLite files and PostgreSQL 17/18 schemas: prior structure with existing rows, empty new tables, nullable and required/defaulted fields, repeated/concurrent startup, changed defaults/nullability, preserved plugin data, and rejection of lost installed fields. Release 0.1.22 also starts the actual 0.1.20 image against PostgreSQL 18 before upgrading with the new image. Folder tests cover notifications/tickets, consent, live permissions, expiration and concurrent link admission.


## Approved browser assistant addition

The first release adds seven empty tables through current DDL and `schemaEvolution`, without changing `doca-2026-10-12-book-payload-storage-v1`: `browser_clipper_profiles`, `browser_clipper_connections`, `browser_clipper_activations`, `browser_clipper_receipts`, `browser_clipper_assistant_sessions`, `browser_clipper_web_sessions`, and `browser_clipper_login_codes`. All original document, permission and configuration rows remain.

Before launch, the owner explicitly approved replacing v1 activation packages / 180-day tokens with website-session-bound authentication. Old v1 configuration, activation and tokens are rejected without conversion. The initial five tables, old credential columns/records, capture profiles, receipts and conversations are preserved; old activation records are inert. The two new tables start empty and receive no inferred grants. Existing mobile, MCP and business-plugin authentication remain separate.

Public site configuration is strict version 2. A 60-second code with a SHA-256 verifier challenge exchanges for 10-minute access, bound to the exact website session and installation connection. Logout and session revocation invalidate access; connection revocation additionally blocks automatic reauthorization until explicitly restored. Browser-origin job IDs separate cancellation from ordinary website jobs in the same conversation. Committed documents and images are never erased by logout, credential rotation or revocation.

The [login acceptance record](verification/browser-clipper-login-2026-10-21/README.md) upgrades actual released 0.2.6 fixtures on SQLite / PostgreSQL 17/18: hashes of 124 original tables retained, seven empty additions, repeated/concurrent startup. Separate fixtures retain prelaunch v1 rows while adding empty session/code tables, reject v1 access, and reject review-required differences without partial writes. Update server, Web and extension together after backing up databases, file volumes and the credential master key. Downgrade needs a separately approved preservation and authorization plan; old binaries could otherwise restore old credential handling. No old-authentication adapter, automatic conversion, table removal or data reset is introduced.
