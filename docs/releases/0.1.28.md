# Doca 0.1.28

[简体中文](0.1.28.zh-CN.md)

Fixes conflicts between knowledge-book acceptance prompts and configured rules, adds explicit human acceptance of known issues, and classifies SDK stream error objects safely instead of displaying `[object Object]` or misidentifying them as content failures.

## Acceptance and human decisions

Reviews follow frozen criterion descriptions and explicit exceptions. IDs such as `grounded` do not impose a Manual-only policy. Explicitly permitted accurate background knowledge must not fail solely because a source omits it. Strict evidence requirements, arithmetic errors and protocol contradictions are still evaluated under the actual rules. Configuration edits do not change an existing run's frozen rules; use a new retry to apply new rules.

Repair tasks with complete candidate content and a valid negative acceptance review offer **Accept known issues and continue**. Users enter the known issues being accepted and confirm the candidate. Original failed checks, failed node status and body remain unchanged; the actor, note and candidate/configuration hashes are audited and included in provenance. The candidate is reused through downstream gates, including publication approval when auto-publication is disabled. Technical failures, missing content and invalid reviews are ineligible.

Publication revalidates the approver, source access, input snapshot and candidate/configuration binding. Invalid or changed inputs block publication. A cancelled continuation can reuse a still-valid decision. Assistant guidance uses actual task capabilities rather than claiming that owner status or another UI bypasses the gate or guessing acceptance causes from an error string.

## Configuration examples and upgrade

Both environment examples explicitly name the existing default SQLite plugin business database path and explain how PostgreSQL deployments replace that path with a separate database and restricted role. Runtime storage layout and historical data are unchanged.

From 0.1.27, stop instances, retain databases, files, configuration and the master key, then deploy matching host and Web builds. No SQL structure changes or historical conversion are introduced. Configuration, workflow and artifacts remain version 1. New decisions record `acceptanceOverride.version=1` in the existing resolution; historical decisions confer no override.

Before rollback, stop new execution and preserve all later writes. 0.1.27 can read the same published artifacts, failed checks and human decisions, but its executor cannot continue the new override flow. Earlier versions still require the [0.1.26 plugin database upgrade procedure](0.1.26.md#required-upgrade-from-0125).
