# 传输层技术 · TCP性能优化
## 第4章 TCP拥塞控制与性能优化
### 学习目标
完成本章学习后，应能够：
1.  掌握传统TCP（RFC5681）与QUIC（RFC9002）拥塞窗口（cwnd）的调整逻辑及状态转换规则；
2.  准确计算带宽时延积（BDP），并理解其与链路最优吞吐量的关系；
3.  分析RTT对TCP性能的影响，以及不同拥塞控制场景下的性能瓶颈来源；
4.  运用网络诊断工具观测并分析TCP拥塞控制的运行状态，排查典型性能问题。

### 核心概念与关键变量
根据RFC5681（TCP拥塞控制标准），TCP发送端维护以下核心状态变量，用于约束发送速率：
| 变量名 | 定义 | 对应 RFC 章节 |
|--------|------|--------------|
| SMSS | 发送端最大分段大小，不含IP/TCP头，基于路径MTU（RFC1191）动态计算 | 2 |
| rwnd | 接收端通告的窗口大小，流量控制的上限 | 2 |
| cwnd | 拥塞窗口，TCP注入网络的最大未确认数据量（受网络拥塞约束） | 2 |
| ssthresh | 慢启动阈值，用于切换慢启动/拥塞避免模式 | 2 |
| flight size | 已发送但未被累积确认的数据量（cwnd与rwnd的最小值即为flight size的实际发送上限） | 2 |
| IW | 初始窗口，三次握手完成后cwnd的初始值 | 3.1 |

> 注：本章未覆盖RFC8311提出的BBR拥塞控制算法，仅基于给定的RFC5681与RFC9002材料，展开传统基于丢包的拥塞控制分析。

### 传统TCP拥塞控制机制（RFC5681）
RFC5681定义了四个核心算法：慢启动、拥塞避免、快速重传、快速恢复，为所有TCP实现的标准规范。

#### 1. 慢启动（Slow Start）
慢启动用于探测网络可用带宽，避免初始发送过量数据导致网络拥塞，是TCP连接建立初期的默认模式。
**必需行为**（遵循RFC2119的MUST关键字）：
- 初始窗口（IW）的设置严格遵循分段数上限：
  - 若SMSS >2190字节：IW最多为2个分段；
  - 若1095 < SMSS ≤2190字节：IW最多为3个分段；
  - 若SMSS ≤1095字节：IW最多为4个分段；
- 初始ssthresh设置为任意大值（默认如65536字节），确保初始阶段cwnd < ssthresh，进入慢启动；
- cwnd调整规则：每收到一个**新数据的累积ACK**，cwnd至多增加SMSS字节（推荐按字节计数：`cwnd += min(N, SMSS)`，N为本次ACK确认的新字节数，用于防御ACK分片攻击，详见RFC3465），因此cwnd呈指数增长。

##### 慢启动示例推演（基于RFC5681规则）
假设场景：SMSS=1460字节（以太网常见MSS，MTU=1500字节减去40字节IP/TCP头），初始ssthresh=65536字节：
1.  初始状态：IW=3×1460=4380字节（满足1095<1460≤2190的规则），cwnd=4380；
2.  第1个RTT：发送3个分段，每个对应ACK到达后，cwnd各加1460 → 累计后cwnd=4380 +3×1460=8760字节；
3.  第2个RTT：发送6个分段（cwnd=8760/1460≈6），每个ACK到达后加1460 → cwnd=8760+6×1460=17520字节；
4.  第3个RTT：发送12个分段，ACK后cwnd=17520+12×1460=35040字节；
5.  第4个RTT：发送24个分段，ACK后cwnd=35040+24×1460=70080字节；
6.  此时cwnd（70080）已超过ssthresh（65536），慢启动结束，进入拥塞避免模式。

#### 2. 拥塞避免（Congestion Avoidance）
当cwnd ≥ ssthresh时，TCP进入拥塞避免模式，以**线性缓慢增长**cwnd，避免过度拥塞，是稳定传输阶段的模式。
**必需行为**（RFC5681 Section3.1）：
- 每经过1个RTT，cwnd最多增加1个SMSS字节（推荐按字节计数：`cwnd += (SMSS²)/cwnd` 每ACK，累计后每RTT增量≈SMSS）；
- 确保飞行大小（已发送但未被累积确认的数据量）不超过拥塞窗口cwnd与接收端通告窗口rwnd的最小值，防止发送过量数据；
- 拥塞控制的核心是让发送速率接近网络的可用带宽，需匹配链路的BDP值（带宽时延积）。

##### 拥塞避免示例推演
延续上述SMSS=1460、cwnd=70080、ssthresh=65536的场景：
1.  当前cwnd=70080，略大于ssthresh=65536，进入拥塞避免；
2.  每处理一个ACK的增量：`(1460²)/70080 ≈ (2,131,600)/70080≈30.4字节`；
3.  每RTT收到的ACK数：70080/1460≈48个，总增量≈48×30.4≈1459字节≈SMSS，符合线性增长规则；
4.  若链路为1Gbps带宽、RTT=100ms，则BDP=125e6字节/秒×0.1秒=12.5MB，当窗口接近 BDP 且接收端、应用与路径均不构成额外瓶颈时，可能充分利用链路；排队、丢包和多流竞争仍需实测。

#### 3. 快速重传与快速恢复（RFC5681 Section3.2）
RTO（重传超时）是传统TCP应对丢包的机制，但超时时间较长，快速重传/恢复是优化方案：
- **快速重传**：当收到3个重复ACK（符合RFC5681 Section2的重复ACK判定规则：ACK无新数据、确认号与上次相同、rwnd相同且有未确认数据），判定为非超时丢包，立即重传丢失分段；
- **快速恢复（RFC5681 的 Reno 基线）**：ssthresh 不大于 max(FlightSize/2,2×SMSS)，快速重传后 cwnd=ssthresh+3×SMSS；每个后续重复 ACK 可再增加一个 SMSS，并在窗口允许时发送。收到确认新数据的 ACK 后 cwnd 回落到 ssthresh。NewReno、SACK 等恢复机制的细节不同，不能混为一套规则。

### QUIC的拥塞控制（RFC9002 NewReno变体）
RFC9002为QUIC定义了基于NewReno的基础拥塞控制，同时QUIC实现可选用其他标准拥塞控制算法，如 CUBIC（RFC9438，替代 RFC8312）等；BBR 是另一类算法，RFC8311 并不是 BBR 规范，与传统TCP存在两点核心差异：
1.  初始窗口：RFC9002 为 min(10×max_datagram_size, max(2×max_datagram_size,14720))；最小拥塞窗口为2×max_datagram_size。
2.  丢包恢复：新的丢包或 ECN 拥塞事件就可降低拥塞窗口；持久拥塞会进一步降至最小窗口。PTO 到期本身不等于检测到丢包，也不直接证明持久拥塞。bytes_in_flight 用于跟踪在途数据。

### 带宽时延积（BDP）与性能优化
带宽时延积（BDP）是衡量链路最优数据承载能力的关键指标，直接决定TCP的最优窗口大小：
\[ BDP = 带宽 × RTT \]
单位通常为字节，代表链路“管道”中可容纳的最大数据量；TCP的最优吞吐量近似为：
\[ 吞吐量 = \frac{cwnd}{RTT} \]
当cwnd接近BDP时，链路被完全利用；若cwnd < BDP，则链路未充分利用；若cwnd > BDP，则会引发丢包导致性能下降。

##### BDP计算示例
假设某链路带宽为100 Mbps，RTT=200ms：
1.  转换带宽单位：100 Mbps =100×10^6 bit/s =12.5×10^6 byte/s；
2.  转换RTT单位：200ms =0.2秒；
3.  BDP=12.5e6 ×0.2=2.5e6字节≈2.44 MB；
4.  因此该链路的最优cwnd应设为约2.5 MB，此时发送速率达到满带宽（约100 Mbps）。

### RTT对TCP性能的影响
RTT是TCP性能的核心瓶颈，主要体现在三个方面：
1.  吞吐量与RTT成反比：相同cwnd下，RTT越大，吞吐量越低；例如cwnd=125,000字节时，RTT=100ms的吞吐量为1.25 Mbps，RTT=200ms时仅为0.625 Mbps；
2.  慢启动效率受RTT限制：长RTT链路中，慢启动每RTT才会增加一次cwnd，导致探测带宽的时间变长，初始发送速率提升缓慢；
3.  重传延迟：RTO（重传超时）基于smoothed_RTT计算，根据RFC6298，RTO = smoothed_RTT + max(G, 4 × RTTvar)，其中G为时钟粒度（通常取值1毫秒），4为RFC6298推荐的常量K，G为时钟粒度，长RTT下RTO会显著增大，丢包后恢复时间变长，性能下降。

### 诊断方法：观测TCP拥塞控制状态
#### Linux环境常用工具与命令
1.  **查看cwnd、ssthresh等状态**：
    ```bash
    # 查看已建立TCP连接的拥塞窗口、慢启动阈值、RTT等信息
    ss -ti state established | grep -E "cwnd|ssthresh|rtt|mss"
    ```
    典型输出：`cwnd=70080 ssthresh=65536 rtt=100.0ms rttvar=10ms mss=1460`

2.  **捕获TCP分段分析丢包**：
    ```bash
    # 捕获目标端口的TCP数据段与ACK，保存为pcap文件供Wireshark分析
    tcpdump -i eth0 -nn tcp port 80 -w tcp_capture.pcap
    ```
    打开后可查看Sequence Number、Acknowledgment Number，判断是否存在重复ACK、丢包事件。

3.  **查看路径MTU与SMSS**：
    ```bash
    # 查看到指定地址的路径MTU
    ip route get 8.8.8.8 | grep mtu
    # 查看TCP连接的SMSS
    ss -ti | grep mss
    ```

### 常见误区与错误配置
1.  **初始窗口违反RFC5681规则**：部分实现可能将IW设置为超过SMSS对应的分段数，导致初始发送过量引发网络拥塞；需严格遵循分段数上限（例如 RFC5681 基线在 SMSS=1460 时为3段；采用 RFC6928 的实现可以采用更大初始窗口，应明确算法与版本）；
2.  **长肥管道的cwnd过小**：对于高带宽长延迟链路（BDP大），默认cwnd过小会导致链路未充分利用；需增大初始窗口，RFC6928（Experimental）允许采用更大的初始窗口，上限为 min(10×SMSS, max(2×SMSS,14600))，不是“至少10段”；若采用传统标准需遵循RFC5681+RFC3390的分段数上限规则；
3.  **错误的ssthresh设置**：将初始ssthresh设为过小值，会过早结束慢启动，导致带宽探测不充分；推荐初始ssthresh设为接收端窗口或大值（如65536字节）；
4.  **未启用SACK**：RFC2018定义的选择性ACK可帮助发送端快速识别丢失分段，减少快速恢复的时间；未启用SACK时，TCP只能依靠重复ACK判定丢包，效率降低约30%以上。

### 安全与边界条件（RFC5681）
1.  **ACK分片攻击防御**：恶意接收端发送多个ACK确认同一分段，诱导发送端按每ACK加SMSS的规则过度增大cwnd，导致网络拥塞；RFC5681推荐的`cwnd += min(N, SMSS)`规则（N为本次ACK确认的新字节数）可有效防御此攻击；
2.  **ECN的合理使用**：显式拥塞通知（RFC3168）可在网络设备标记CE位，而非丢包，提前通知发送端拥塞，减少不必要的cwnd降低，提升性能约20%；
3.  **边界条件**：当飞行大小（bytes_in_flight）小于cwnd时，说明应用层数据不足，此时不应增大cwnd（RFC9002 Section7.8），避免无效发送；若cwnd小于最小窗口值，需调整应用层的发送数据量。

### 自测题（含解析）
1.  **基础题**：根据RFC5681，当SMSS为1460字节时，初始窗口（IW）的最大分段数是多少？对应字节数是多少？
    **解析**：SMSS=1460字节，满足1095 < SMSS ≤2190的条件，因此IW最大分段数为3；对应字节数=3×1460=4380字节，符合RFC5681的规则。
2.  **应用题**：某链路带宽为1Gbps，RTT=150ms，计算该链路的带宽时延积（BDP），并说明TCP最优发送窗口的近似值。
    **解析**：1Gbps=125e6字节/秒，RTT=0.15秒，BDP=125e6×0.15=18.75e6字节≈17.88MB；TCP最优发送窗口应接近BDP，即约18MB，只有在接收窗口、应用供给、CPU、路径容量及丢包等条件都允许时，才可能接近该吞吐量；BDP 是估算参考，不是保证。
3.  **原理题**：当TCP收到3个重复ACK时，触发的快速重传/快速恢复机制与传统RTO超时重传相比，核心优势是什么？
    **解析**：核心优势在于**不需要等待RTO超时**（RTO 由平滑 RTT、RTT 波动与时钟粒度计算，RFC6298 基线有1秒下限；实现可能不同，不能固定写成 RTT 的2到4倍），可在RTT量级的时间内完成丢包恢复，大幅减少恢复时间，尤其适合短连接或低延迟链路；同时快速恢复阶段不会像传统TCP那样将cwnd重置为SMSS，避免了发送速率的过度下降，提升了恢复后的传输效率。
