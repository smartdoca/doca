# TCP序号、确认、重传与流量控制
## 学习目标
本章聚焦TCP可靠性传输的核心基础机制，旨在让读者掌握：
1. TCP**有序字节流与累积确认模型**的设计逻辑，理解序号与确认号的作用边界；
2. TCP重传机制的触发条件与实现差异（超时重传 vs 快速重传）；
3. 滑动窗口流量控制的原理（含拥塞窗口cwnd和接收窗口rwnd的共同限制）与工程表现，能解读窗口值的动态调整；熟悉现代TCP拥塞算法（如CUBIC、BBR）的基本特性，这些算法是当前主流操作系统的默认实现（RFC8312、RFC9002）；
4. 掌握通过工具（Wireshark、ss等）观测与诊断TCP传输问题的方法。
本章内容基于RFC9293核心规范展开，未包含RFC3168定义的ECN（显式拥塞通知）扩展细节（对应原始资料缺口说明）。

## 核心机制与关键报文字段
TCP的可靠性建立在**全局连续字节序列**与**累积确认**两大核心假设之上，所有机制围绕这两点设计。

### TCP报文字段（RFC9293第3.1节）
下表总结与本章直接相关的关键字段及控制位，需明确其语义边界：
| 字段/控制位 | 长度 | 规范定义 |
|-------------|------|----------|
| 源端口/目的端口 | 各16位 | 标识连接两端的应用进程，用于多路复用 |
| 序号（Seq） | 32位 | 本段**第一个数据字节**的全局序号；若SYN控制位置位，该值为初始序号（ISN），且SYN控制位**占用1个序号空间**（后续数据从ISN+1开始） |
| 确认号（Ack） | 32位 | 仅当ACK控制位置位时有效；表示期望对端发送的下一个字节的序号，即**已成功接收对端到[Ack-1]的所有字节**（累积确认特性） |
| 控制位（Flags） | 8位（8个标记位） | 本章核心涉及：<br>• `SYN`：连接初始化同步（占用1个序号）<br>• `ACK`：确认号有效（连接建立后需始终置位）<br>• `FIN`：连接终止（占用1个序号）<br>• `RST`：强制重置连接（不占用序号） |
| 窗口（WND） | 16位（基础版） | 本端当前可接收的连续字节数（从Ack号计数），即流量控制的窗口大小；若启用窗口缩放（RFC1323），该值需乘以协商的缩放因子，RFC9293中明确“窗口值需按规则移位后才是实际可接收字节数” |

### 序列空间（RFC9293第3.3节图3、图4）
TCP连接两端维护两组动态变量，跟踪发送与接收的状态边界，所有序号操作基于**模2³²的无符号算术**（序号空间回绕时需用此规则判断）：
#### 发送序列空间变量（本端作为发送方）
- `SND.UNA`：已发送但未被对端确认的最小序号（ oldest unacknowledged sequence number）
- `SND.NXT`：本端下一个待发送字节的序号（ next sequence to send）
- `SND.WND`：本端接收窗口大小（来自对端Ack段中的Window值，反向控制发送速率）
发送窗口的合法范围为 `[SND.UNA, SND.UNA + min(SND.WND, cwnd) -1]`，仅该范围内的序号可被发送；其中 SND.WND 是对端通过ACK段通告的接收窗口，cwnd 是TCP维护的拥塞窗口（根据网络动态调整），实际发送能力由两者的最小值决定，这是TCP拥塞控制的基础（RFC5681）。

#### 接收序列空间变量（本端作为接收方）
- `RCV.NXT`：期望从对端接收的下一个字节的序号（接收窗口左边界）
- `RCV.WND`：本端接收缓冲区剩余空间（可接收的字节数），接收窗口范围为 `[RCV.NXT, RCV.NXT + RCV.WND -1]`，仅该范围内的段可被接收（避免数据重叠或丢弃）。

## 数值推演实例（严格基于RFC9293规则）
以下实例均遵循规范定义，无虚构实测结果，所有数值符合序列空间约束：

### 实例1：三次握手与初始序号分配
TCP连接建立需同步双方初始序号（ISN），每侧ISN独立生成，三次握手的序号逻辑（RFC9293第3.4.2节）：
1. 客户端→服务器：`SYN`段，`Seq=ISN_C=1000`，`SYN=1`（SYN占用1个序号，故后续数据从1001开始），无数据。
2. 客户端←服务器：`SYN+ACK`段，`Seq=ISN_S=2000`，`ACK=1`，`Ack=ISN_C+1=1001`（服务器确认客户端的初始序号）。
3. 客户端→服务器：`ACK`段，`Seq=1001`，`ACK=1`，`Ack=2001`（客户端确认服务器的初始序号）。
连接建立后，双方序列空间状态：
- 客户端：`SND.UNA=1000`，`SND.NXT=1001`，`RCV.NXT=2000`
- 服务器：`SND.UNA=2000`，`SND.NXT=2001`，`RCV.NXT=1001`

### 实例2：数据传输与累积确认
客户端向服务器发送2500字节数据，分两段传输：
1. 第一段：`Seq=1001`，长度=1000字节（覆盖字节1001~2000），发送后`SND.NXT=2001`。
2. 第二段：`Seq=2001`，长度=1500字节（覆盖字节2001~3500），发送后`SND.NXT=3501`。
服务器接收两段后分别返回确认：
- 接收第一段后：`ACK=2001`（表示已到序号2000，期望下一个是2001），客户端`SND.UNA=2001`。
- 接收第二段后：`ACK=3501`，客户端`SND.UNA=3501`，所有数据确认完成。

### 实例3：丢失段的重传触发
若第二段（`Seq=2001`，长度1500）在传输中丢失，会触发三种符合规范的重传与恢复机制：
1. **超时重传（RTO）**：客户端动态计算RTT（往返时间）后，等待RTO时间未收到第二段的确认，则重传`Seq=2001`的段，`SND.NXT`仍为3501（本例尚无更新数据），重传不把“下一个新数据序号”倒退；`SND.UNA`才表示最早未确认字节。
2. **快速重传**：若作为发送方的客户端收到符合条件的3个重复ACK（因未收到第二段，确认号无法推进，导致重复ACK），客户端无需等待超时，直接重传丢失段（快速重传和 Reno 快速恢复见 RFC5681 §3.2；NewReno 是相关但不同的恢复扩展）。
3. **选择性确认（SACK）**：若TCP选项中携带SACK块（RFC2018），发送方获知接收端已收到的不连续字节区间，再结合确认和丢失检测推断缺口；SACK 并非直接列出丢失报文，减少不必要的重传，大幅提升高丢包网络下的传输效率。

### 实例4：滑动窗口流量控制
假设服务器接收缓冲区初始为4000字节，初始窗口`SND.WND=4000`（来自服务器的ACK段）：
- 客户端发送第一段（1000字节）后，服务器接收缓冲区剩余3000字节，返回的ACK段中`WND=3000`，客户端后续仅能发送不超过3000字节的数据。
- 客户端发送第二段（1500字节）后，服务器接收缓冲区剩余1500字节，ACK段中`WND=1500`，发送速率被进一步限制。
- 若服务器应用程序读取了1500字节，接收缓冲区剩余空间增加，会通过ACK段将`WND`更新为更大值（如4000），允许客户端继续发送。

## 观测与诊断方法
### 1. 抓包分析（Wireshark/tcpdump）
通过抓包直接观测TCP段的字段，核心操作：
- 捕获命令：`tcpdump -i eth0 tcp port 80 -w tcp_trace.pcap`（捕获端口80的TCP流量）。
- Wireshark分析：打开pcap文件，选中段后展开`Transmission Control Protocol`层，可查看：
  - `Sequence number`（对应字段Seq）、`Acknowledgment number`（对应Ack）；
  - `Window size value`（基础窗口，需结合窗口缩放计算实际值）。

### 2. TCP连接状态查询（Linux `ss`工具）
`ss`替代`netstat`可查看TCP内部序列空间变量，命令示例：
```bash
ss -ti dst 192.168.1.100:80
```
输出中关键信息解读：
- `snd:una:1001` → `SND.UNA=1001`
- `snd:nxt:3501` → `SND.NXT=3501`
- `rcvwnd:4000` → `RCV.WND=4000`
- `rtt:20ms` → 动态计算的往返时间，用于重传超时控制。

### 3. 常见问题诊断
- **乱序段**：Wireshark中显示段的`Seq < RCV.NXT`，说明段乱序，需排查网络是否存在多路径或乱序转发。
- **零窗口**：`ss`输出`rcvwnd:0`，说明接收缓冲区满，发送方会暂停发送，需确认应用是否及时读取数据。
- **频繁重传**：Wireshark中`Retransmitted segments`占比超过5%，需排查链路丢包或RTT计算异常。

## 常见误区与边界处理
### 核心误区
1. **序号与段内偏移混淆**：序号是连接全局的，例如Seq=1001的段，即使长度为1000，其最后一个字节是1001+1000-1=2000，而非段内偏移1000。
2. **忽略序号模2³²特性**：当序号接近2³²-1时，`Seq2 > Seq1`的简单比较会失效，需用RFC9293定义的规则判断（如“可接受确认需满足`SND.UNA < Ack <= SND.NXT`”）。

### 边界情况
- **序号回绕**：当连接传输数据超过2³²字节时，序号会回绕到0，TCP实现需用模运算处理序号比较，否则会出现确认逻辑错误。
- **零长度段**：TCP允许长度为0的段（仅含ACK控制位），此时`SEG.LEN=0`，不占用序号空间，接收方需单独处理这类段（RFC9293第3.4节）。
- **窗口缩放**：RFC1323定义窗口缩放，SYN段中协商缩放因子S，实际窗口值为`Window值 × 2^S`，RFC9293中说明基础窗口为16位，缩放为可选扩展。

## 安全与规范边界
1. **序号预测攻击**：早期TCP ISN生成规则简单（如线性递增），攻击者可预测ISN劫持连接。当前RFC4987要求ISN为伪随机数，但仍需警惕连接伪造风险。
2. **SYN洪水攻击**：攻击者发送大量SYN段，占用服务器TCB资源，导致正常连接无法建立，缓解措施为SYN Cookie（RFC4987）。
3. **窗口攻击**：恶意方发送极小窗口或零窗口段，迫使发送方暂停传输，需实现合法窗口更新的验证逻辑（仅响应对端的窗口调整请求）。

## 自测题与解析
1. **基础计算**：TCP段的Seq=2000，长度=800字节，该段最后一个字节的序号是多少？
   解析：根据RFC9293第3.4节“SEG.SEQ+SEG.LEN-1”规则，答案为`2000 +800 -1=2799`。SYN/FIN段因长度L=1（控制位占用序号），同理适用此规则。
2. **确认有效性判断**：TCP连接的SND.UNA=1001，SND.NXT=2500，收到Ack=2001，该确认是否合法？
   解析：合法。根据RFC9293第3.4节“可接受确认”规则：`SND.UNA < Ack <= SND.NXT`，代入得1001 <2001 ≤2500，满足条件。
3. **接收段有效性判断**：接收方RCV.NXT=2000，RCV.WND=1000，下列哪些段会被接收？（多选）
   A. Seq=2000，长度=500 → 段范围2000-2499，落在[2000,2999]内 → 接收
   B. Seq=2500，长度=500 → 段范围2500-2999，落在[2000,2999]内 → 接收
   C. Seq=3000，长度=100 → 段范围3000-3099，超出 → 不接收
   D. Seq=1500，长度=1000 → 段范围1500-2499，部分在窗口外 → 不接收
   答案：A、B（依据RFC9293第3.4节接收判断规则：段起点或终点需落在接收窗口内）。
