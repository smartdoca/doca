# IPsec：VPN与隧道安全机制
## 学习目标
1. 区分IPsec的AH与ESP协议核心功能、适用场景，明确两者在安全服务上的本质差异
2. 对比IPsec传输模式与隧道模式的工作逻辑，掌握隧道模式在站点间VPN、远程访问VPN中的部署依据
3. 理解IPsec安全关联（SA）的单向性与标识规则，能通过核心字段判断SA的有效性与状态
4. 掌握IPsec VPN的核心安全特性（数据源认证、完整性、抗重放、机密性）的实现原理，能基于RFC规范分析安全边界

---

## 核心机制解析（基于RFC4301）
### 1. IPsec基础框架与两类安全协议
根据RFC4301（IP安全体系结构，2005年发布）定义，IPsec通过**网络层**的密码学保护，为IPv4/IPv6提供端到端或站点间的安全服务，核心组件包括安全协议（AH/ESP）、安全关联（SA）、密钥管理（IKE）三大模块；IPsec实现必须支持ESP协议，AH协议为可选支持。

IPsec提供的安全服务包括：数据源认证（验证报文来源合法性）、数据完整性（验证报文未被篡改）、抗重放（防止捕获报文后重放攻击）、机密性（加密报文内容）。两类安全协议的对比如下表：

| 特性维度                | AH协议（RFC4302定义，基于RFC4301） | ESP协议（RFC4303定义，基于RFC4301） |
|-------------------------|-----------------------------------|------------------------------------|
| 核心安全服务            | 数据源认证、数据完整性，抗重放为可选特性（可由接收方决定是否启用），无加密 | 机密性（加密Payload）+ 数据源认证、完整性、抗重放 |
| 保护范围                | IPv4：IP头可变字段（如TOS、标志位除外）+ 整个Payload；IPv6：扩展头可变字段除外 | 仅ESP封装的Payload部分，外IP头未受保护 |
| IP协议号标识            | 51                                | 50                                 |
| 典型应用场景            | 路由协议、控制平面报文（无需加密仅需强认证） | 站点间VPN、远程访问VPN（需机密性保护） |

> 注：AH的认证范围不包含IP头中中间网络可修改的字段（如TTL），中间路由器正常修改这些字段不会因此导致 AH 校验失败；而ESP的加密特性决定了其是当前IPsec部署的首选协议（RFC4301 Section 2.2明确：多数安全需求可通过ESP单独满足）。

### 2. IPsec的两种工作模式
RFC4301 Section 4.1定义了AH与ESP支持的两种模式，核心差异在于是否封装整个IP报文：
#### （1）传输模式
- 适用场景：**主机到主机的端到端安全通信**
- 工作逻辑：安全协议头（AH/ESP）插入在原IP头（IPv4/v6）与上层协议头（TCP/UDP）之间，仅保护上层协议的数据，原IP头未被保护（ESP传输模式仅加密上层Payload，原IP头明文）
- 报文结构（IPv4）：原IP头 → AH/ESP头 → TCP头 → Payload → 认证数据

#### （2）隧道模式
- 适用场景：**站点间VPN、主机到安全网关的远程访问VPN**
- 工作逻辑：将整个原IP报文作为Payload封装，新增一个外部IP头（由安全网关/隧道端点生成），安全协议头插入在外部IP头与内部IP头之间；内部IP头携带真实源/目的地址，外部IP头为隧道端点地址
- 报文结构（ESP隧道模式）：外部IP头（隧道端点地址）→ ESP头 → 内部IP头（真实源/目的）→ TCP头 → Payload → ESP尾（填充等）→ 完整性校验值（ICV）

RFC4301 Section 4.1明确**必需行为**：当SA的任意一端为安全网关时，必须使用隧道模式；主机实现必须同时支持传输与隧道模式，安全网关实现必须支持隧道模式（可选支持传输模式）。

#### 模式差异示例推演
假设站点A（内网：192.168.1.0/24，公网IP：203.0.113.1）与站点B（内网：10.0.0.0/24，公网IP：198.51.100.1）建立IPsec VPN，用ESP隧道模式访问：
1. A内部主机（192.168.1.1）访问B内部主机（10.0.0.1），生成原IP包：源192.168.1.1，目的10.0.0.1，协议6（TCP）
2. A的安全网关收到该包后，匹配IPsec策略，封装为隧道模式包：
   - 外部IP头：源203.0.113.1，目的198.51.100.1，协议50（ESP）
   - ESP头：SPI=0xabcdef12（SA标识）、序列号=100（抗重放用）
   - 内部IP头、TCP头、Payload、ESP尾、ICV（认证数据）
3. 该包经公网传输，中间路由器仅能看到外部IP头，无法获取内部拓扑，实现内网隐藏与加密

### 3. 安全关联（SA）：IPsec的核心管理单元
RFC4301 Section 4.2定义SA为单向的逻辑连接，是IPsec处理报文的基础：SA唯一标识由**三元组**确定：
- SPI（Security Parameter Index，32位）：本地生成的随机数，区分同一目的IP/协议的多个SA
- 目的IP地址：SA对端的IP地址
- 安全协议：AH（51）或ESP（50）

**关键特性**：双向通信需要2个独立的SA（入方向SA和出方向SA），例如A到B的流量对应1个SA，B到A的流量对应另1个SA。SA的生命周期由密钥、字节数、时间等参数控制，过期后需重新协商。

SA的核心字段（可通过Linux `ip xfrm state`命令查看）：
| 字段               | 含义                                  | RFC4301要求 |
|--------------------|---------------------------------------|-------------|
| mode               | 隧道/传输模式                          | MUST包含    |
| replay-window      | 抗重放窗口配置（支持至少32，推荐64或更大）        | MUST包含    |
| auth-trunc         | 认证算法及密钥（如hmac-sha256）        | MUST包含    |
| enc（ESP特有）     | 加密算法及密钥（如aes-128-cbc）        | MUST包含    |
| life-time          | SA的生命周期（时间/字节数限制）        | MUST包含    |

## VPN场景下的IPsec安全特性
IPsec VPN的核心安全特性基于隧道模式与SA实现，具体如下：
1. **数据源认证与完整性**：ESP/ AH通过HMAC算法（如SHA-256）生成ICV（完整性校验值），接收端校验ICV，验证报文来源是否合法、是否被篡改
2. **抗重放攻击**：实现须支持抗重放，是否对特定 SA 启用由接收方选择。启用后维护滑动窗口，丢弃已收到的重复序号及窗口左侧过旧序号；合法的新高序号验证通过后推进窗口，不是“窗口外一律丢弃”。窗口大小不是固定32，RFC4302/4303规定至少支持32并推荐64，工程实现可以更大。
3. **机密性**：ESP通过对称加密算法（如AES）加密Payload，仅隧道端点可解密，中间网络无法获取报文内容
4. **访问控制**：通过IPsec安全策略数据库（SPD）匹配流量，仅符合策略的流量会被IPsec保护，未匹配的流量直接放行（RFC4301 Section 4.4.1）

## 可操作的观测与诊断方法
### 1. 关键观测命令（Linux环境）
IPsec的SA与SPD可通过标准Netlink命令（`ip xfrm`）观测，是诊断VPN问题的核心工具：
```bash
# 查看所有已建立的SA（重点关注mode、proto、spi、状态）
ip xfrm state list

# 查看安全策略数据库（SPD，匹配流量是否触发IPsec）
ip xfrm policy show
```
#### 示例输出解析（ESP隧道模式SA）：
```
src 203.0.113.1 dst 198.51.100.1
        proto esp spi 0xabcdef12 reqid 1 mode tunnel
        replay-window 32
        auth-trunc hmac(sha256) 0xabc...128 128
        enc aes 0xdef...456 128
        life-time 3600s
        state active
```
- `mode tunnel`：确认是隧道模式（符合站点VPN要求）
- `state active`：SA已激活，可正常使用
- `replay-window 32`：抗重放机制正常启用

### 2. 常见诊断场景
| 问题现象                | 诊断步骤（基于RFC4301要求） |
|-------------------------|------------------------------|
| VPN不通，SA未建立       | 1. 检查IKE协商是否成功（如`swanctl --list-sas`，libreswan用`ipsec status`）；2. 检查SPD规则是否匹配流量；3. 确认两端公网IP/端口（ESP 50、IKE 500/4500 UDP）是否开放 |
| 部分报文丢包             | 1. 查看SA的replay-window，是否存在重复序列号（重放攻击触发）；2. 检查MTU（隧道模式会增加IP头，需调整MTU避免分片）；3. 确认SA生命周期是否过期 |
| 认证失败（ESP/AH）       | 1. 检查两端加密/认证算法是否一致；2. 检查密钥是否匹配；3. 确认报文是否被篡改（NAT 修改受保护字段或认证数据被改变） |

## 常见误区与安全边界
### 1. 典型误区
- **误区1：AH和ESP都加密**：AH仅提供认证，无加密能力，适合控制平面报文，ESP才提供机密性（RFC4301 Section 2.2明确）
- **误区2：SA是双向的**：SA是单向的，双向通信需要2个独立SA，需IKE分别协商入方向和出方向SA
- **误区3：隧道模式只能用于网关**：RFC4301 Section 4.1说明两个主机也可建立隧道模式SA，仅网关必须使用隧道模式

### 2. 安全边界（基于RFC4301）
- IPsec**无法处理IPv4分片的传输模式报文**：仅隧道模式支持分片处理（RFC4301 Section 4.1的必需限制），若主机用传输模式处理IPv4碎片会导致认证失败
- AH的认证范围不包含IP头可变字段：可变字段按规则规范化，不因正常 TTL 递减而失败；NAT 修改受保护的地址字段则会影响验证，应具体分析覆盖范围
- 密钥管理依赖IKE：SA的密钥由IKE协商生成，手动配置密钥易泄露，RFC4301推荐自动密钥管理（IKEv2）

## 自测题（附答案与解释）
### 题1：IPsec SA的唯一标识三元组是？（单选）
A. 源IP、目的IP、IP协议号  
B. SPI、目的IP、IPsec协议（AH/ESP）  
C. 源端口、目的端口、SPI  
D. 源IP、目的IP、SPI  

**答案：B**  
解释：RFC4301 Section 4.2明确，SA的唯一标识由SPI（本地32位随机数）、SA对端目的IP、安全协议（AH/ESP）组成，三者共同确定一个单向SA，因此选B。

### 题2：下列关于IPsec隧道模式的描述，错误的是？（多选）
A. 隧道模式封装整个内部IP报文，隐藏内网拓扑  
B. 安全网关与安全网关之间的SA必须使用隧道模式  
C. 隧道模式仅支持加密，不支持认证  
D. 传输模式的安全协议头在原IP头之后，隧道模式在外部IP头与内部IP头之间  

**答案：C**  
解释：RFC4301 Section 2.2说明，隧道模式使用ESP时可同时提供加密、认证、抗重放，C选项错误；A、B、D均符合RFC规范。

### 题3：IPsec AH协议的核心服务不包括？（单选）
A. 数据源认证  
B. 数据完整性保护  
C. 报文机密性（加密）  
D. 抗重放攻击  

**答案：C**  
解释：RFC4302（AH协议规范）明确，AH仅提供数据源认证、完整性、抗重放，无加密能力，机密性由ESP提供，因此选C。
