# DNS记录类型、缓存与变更排障

DNS 运维的核心不是“改完记录后等一会儿”，而是辨认回答来自哪一层、哪一个区域版本以及哪份仍有效的缓存。本章以 `example.com` 为示例域，说明记录、缓存、变更与排障之间的关系。示例地址使用文档保留地址，实际操作时替换为自己的测试域与服务器。

## 一、先区分名称、区域、记录集

域名是名称空间中的节点；区域是由一组权威服务器管理的连续范围；委派把某个子域交给另一组权威服务器。一个名称可以拥有多个类型的记录，但区域边界与字符串后缀并不总是一回事。查 `api.example.com` 时，应该先确定其权威区域，不能只把所有请求发到 `example.com` 的某一台服务器。

资源记录的基本结构是 `NAME TYPE CLASS TTL RDATA`。同名称、同类型、同类的一组记录构成 RRset；例如同一服务配置两个 A 地址，是一个 A RRset。缓存与 DNSSEC 验证都需要正确处理记录集，不能把不同时间获得的不一致记录任意拼接。记录的 TTL 表示可缓存时长，不是健康检查、连接超时，也不是服务自动切换的保证。

|类型|编号|用途|运维边界|
|---|---:|---|---|
|A|1|名称到 IPv4 地址|多个地址不等于具备主动健康检查的负载均衡|
|AAAA|28|名称到 IPv6 地址|A 正常并不能证明 IPv6 路径正常|
|NS|2|区域权威服务器名称与委派|父区委派与子区顶点 NS 需要保持一致|
|CNAME|5|名称别名|别名节点通常不能同时放其他普通数据；区域顶点必须有 SOA/NS，因此不能简单配置普通 CNAME|
|SOA|6|区域管理信息与负缓存参数|serial 是区域版本标识；refresh/retry/expire 主要用于从服务器维护，不是普通记录 TTL|
|PTR|12|反向地址查询|正反向记录由不同区域维护，彼此不会自动生成|
|MX|15|邮件服务器与优先级|数值越小越优先，目标应能解析到地址，不应指向 CNAME|
|TXT|16|文本数据，如域名验证、邮件策略|没有统一的业务语义，需由使用它的协议解释|
|SRV|33|服务目标、端口、优先级与权重|客户端必须支持该服务发现方式才能使用|
|CAA|257|限制允许签发证书的 CA|属于证书签发策略，不替代 TLS 客户端的证书验证|

AAAA、SRV、CAA 分别参见 RFC3596、RFC2782、RFC8659。基础记录格式参见 RFC1035 §3；CNAME/RRset 的约束参见 RFC2181 §5、§10。查询中的 QTYPE 可以是记录类型，也可以有查询专用值；不要把 TYPE 错理解成“只出现在响应中”。

## 二、正缓存与负缓存

典型链路是：应用自身缓存 → 操作系统解析服务 → 递归解析器 → 权威服务器。实际系统也可能由浏览器通过 DoH 使用另一台解析器。每层的缓存与刷新接口不同，清除本机缓存不会清除公司 DNS、公共递归服务器或浏览器自己的缓存。

### 2.1 正缓存的时间线

假设权威服务器在 12:00 返回 `www.example.com. 3600 IN A 192.0.2.10`。递归解析器此时缓存记录，12:10 再返回时通常附带约 3000 秒的剩余 TTL，而不是重新赋予完整 3600 秒。管理员在 12:15 把权威地址改成 `192.0.2.20`，已缓存旧记录的解析器一般仍可在剩余有效期内返回旧地址。

不同解析器最初缓存的时刻不同，所以不会在一个全球统一时刻切换。某些解析器实施预取、TTL 上下限或故障时提供过期数据的策略；RFC8767 讨论了 serve-stale。TTL 也不能关闭已经建立的 TCP 连接或清空应用连接池。因此“TTL 已到但仍访问旧服务”需要继续检查应用解析路径和连接复用。

TTL 为 0 表示结果不应被常规缓存用于后续查询，但会增加查询量和对 DNS 服务可用性的依赖，不能靠设成 0 获得绝对实时切换。

### 2.2 NXDOMAIN 与 NODATA

- **NXDOMAIN**：响应码为 3，表示被查询名称不存在。CNAME 场景下要注意回答描述的最终名称。
- **NODATA**：名称存在，但所问类型不存在；通常为 `NOERROR`、空 Answer，并带有用于否定回答的 SOA。NODATA 不是一种独立响应码。
- **SERVFAIL**：解析失败，可能来自验证失败、上游超时或其他问题；不能把它解释为“名称不存在”。

RFC1034 最初讨论负缓存时有可选语义，RFC2308 后来明确要求缓存解析器实现负缓存，并规定缓存粒度与寿命。不能仅按早期 RFC1034 描述现代实现。

**负缓存初始 TTL = min(SOA 记录自身的 TTL, SOA.MINIMUM)。** 权威服务器在否定回答中携带适当的 SOA；解析器转发已缓存否定回答时应扣减剩余时间。无合适 SOA 的否定回答不应按普通长期负缓存处理。参见 RFC2308 §3、§5。

例如某区域 SOA 记录自身 TTL 为 600 秒，RDATA 中最后一个 `MINIMUM` 为 3600 秒：

```dns
example.com. 600 IN SOA ns1.example.com. hostmaster.example.com. (
  2026092701  ; serial
  3600        ; refresh
  600         ; retry
  1209600     ; expire
  3600        ; minimum
)
```

在此情况下，一次 NXDOMAIN 回答的负缓存初始寿命为 **600 秒**，不是 3600 秒。五分钟后，未受其他实现策略影响的缓存剩余时间约为 **300 秒**。这时即使管理员创建了该名称，已经保存否定结果的解析器仍可能在剩余寿命内回答 NXDOMAIN。现在降低权威服务器上的参数，不会追溯修改远端已经缓存的剩余 TTL。

## 三、可靠的 DNS 变更流程

以计划迁移 A/AAAA 地址为例：

1. **盘点依赖。** 记录旧地址、权威服务器、委派、原 TTL、AAAA、相关 CNAME 链、客户端是否使用专用 DoH，以及服务端 TLS 证书和新地址可用性。
2. **提前降低 TTL。** 在真正改地址之前将相关记录 TTL 降到合适值，例如测试环境的 60 秒；至少为可能仍持有旧 TTL 的缓存留出原 TTL 的等待窗口。60 秒是示例，并非标准要求。
3. **准备新目标。** 确认新目标的路由、防火墙、TLS 和应用健康；旧目标继续服务以覆盖迁移窗口。
4. **修改记录并核对所有权威节点。** 检查 A 与 AAAA、SOA serial 和多个权威实例的一致性；只核对管理控制台不够。
5. **观察不同解析路径。** 对比企业递归、公共递归、系统解析与浏览器实际结果，同时监控错误率、流量落点和连接复用。
6. **稳定后恢复 TTL。** 根据可用性和变更频率恢复长期策略。恢复较长 TTL 应在地址迁移验证完成后进行，而不是在改地址之前。

新建一个此前查询过的名称时，还应提前考虑负缓存的寿命。CNAME 链有多个 RRset，各段独立缓存；只修改其中一段 TTL 不会清除其他段。若出现异常，回滚记录同样受缓存影响，需要保留新旧服务并行或应用层回退方案。

## 四、从权威到客户端逐层取证

### 4.1 明确查询对象与返回标志

```sh
# 查询指定递归解析器；观察 Answer、Authority、status 和剩余 TTL
dig @192.0.2.53 www.example.com A

# 直接查询实际权威服务器，并明确不请求递归
dig @ns1.example.com www.example.com A +norecurse

# 同样检查 IPv6 与区域管理信息
dig @ns1.example.com www.example.com AAAA +norecurse
dig @ns1.example.com example.com SOA +norecurse

# 查看委派链路，用于发现父区、子区、胶水地址问题
dig example.com NS +trace
```

`+norecurse` 仅把 RD 位清零，**不是清缓存或强制绕过缓存的开关**。如果目标是一台递归解析器，它仍可能返回已有缓存。要检查权威内容，必须选对实际权威服务器，并检查响应的 `AA` 标志、区域和名称。普通 `dig` 命令本身不维护可供下一次独立调用使用的持久 DNS 缓存，没有通用的 `+nocache` 参数。

`+trace` 显示迭代查询过程，但不等同于应用真实解析路径，也不自动证明每份数据可信。DNSSEC 验证、DoH/DoT 传输加密以及正确查询权威对象是不同层面的措施。

### 4.2 缓存定位

在使用 systemd-resolved 的 Linux 主机上，可用 `resolvectl status` 查看实际 DNS 配置，`resolvectl statistics` 查看统计，`resolvectl flush-caches` 清除该服务的本地缓存。缓存枚举命令随 systemd 版本不同，应先看 `resolvectl --help`，不要假设每台机器都有 `show-cache`。Windows 可使用 `ipconfig /displaydns` 与 `ipconfig /flushdns`。

清缓存前先记录故障答案与 TTL，否则会失去关键证据。清完本机仍看到旧答案时，继续对比指定递归服务器，而不是重复清本机。浏览器、JVM、代理、容器和服务网格还可能各有独立解析路径。

### 4.3 故障判定表

|现象|优先验证|可能原因与下一步|
|---|---|---|
|所有权威节点都是旧记录|查询对象、区域与 serial|修改了错误区域，或发布尚未完成|
|不同权威节点回答不同|逐台查询 SOA 与记录|区域同步、隐藏主服务器、Anycast 实例配置差异|
|权威已更新，递归仍旧|递归答案的剩余 TTL|正常旧缓存；过期后仍旧再查 serve-stale、转发链和策略|
|A 正确但连接间歇失败|AAAA 与 IPv6 路径|客户端优先选择或并行尝试 IPv6，不能只测 A|
|刚创建名称仍 NXDOMAIN|Authority 中 SOA 与剩余负 TTL|已有负缓存；等待剩余寿命或处理可控解析器缓存|
|NOERROR 但没有所问记录|QTYPE、CNAME、Authority|NODATA 与委派回答需要区分|
|SERVFAIL 且权威可达|DNSSEC 验证日志、时间、DS/DNSKEY|签名链或验证失败，不能当成普通 NXDOMAIN|
|DNS 已正确，仍到旧后端|实际连接目标与连接池|长连接、代理缓存、hosts 或应用硬编码地址|

## 五、容易误用的配置

**通配符不是万能后缀匹配。** `*.example.com` 的合成受现存名称、最近存在祖先和委派边界影响；具体名称存在但缺某个记录类型时，不应想当然认为会回退到通配符。参见 RFC4592。

**权威与递归职责要区分。** `AA=1` 表示权威回答，`RA=1` 表示服务器声明支持递归，`RD=1` 表示客户端请求递归；这些标志不是同一个意思。收到应答也不等于其身份经过密码学认证。

**记录集 TTL 要一致。** 同一 RRset 不应配置相互冲突的 TTL。CNAME、目标 A/AAAA、父区委派和胶水记录是不同对象，可能有各自的缓存生命周期。

## 六、带解析的自测

1. SOA TTL 为 900、MINIMUM 为 300，一次新的否定回答应按哪个值计算？
   - 按两者较小值 300 秒，随后缓存转发会扣减寿命。不是只看 SOA 的最后一列。
2. `dig @recursive.example www.example.com A +norecurse` 能保证拿到最新权威答案吗？
   - 不能。RD=0 不清缓存；目标递归服务器可能只返回缓存或拒绝处理。应定位并直接查询权威服务器，核对 AA。
3. 原 TTL 为 3600，刚把它改成 60，马上迁移地址是否只需等 60 秒？
   - 不能保证。远端旧缓存可能仍按原剩余寿命存在，需要提前降低并等待旧窗口。
4. 所有 DNS 查询都返回新 IP，为什么客户端仍请求旧 IP？
   - 排查进程自己的解析缓存、代理、hosts、硬编码地址和已经建立的连接；DNS TTL 不终止连接。
